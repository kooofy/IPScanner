# IPScanner 代码全面分析与改进意见（v1.8.0 基线）

> 本文是「跳出既有建议书」的一次独立通读。目标不是复述 `PRODUCT_ADVISORY.md`  
> （那份已对标 10+ 款同类产品、且大部分已在 v1.8.0 落地），而是：
>
> 1. 核实 v1.8.0 到底交付了什么（有没有"文档说做了、代码没跟上"）；
> 2. 找出建议书与路线图**没有覆盖**、或**判断已经过时**的盲点；
> 3. 给出 v1.9 / v2 之后真正值得做的增量建议，按投入产出比排序。
>
> 基线：`kooofy/IPScanner` @ `3188f69`（v1.7.5）之后、`1.8.0` 之后的工作树。  
> 所有"已核实"结论均来自本次读代码；未核实处会明确标注。

---

## 0. 结论先行（30 秒版）

**这个项目的工程质量已经超过绝大多数同类开源/个人项目**，不是"要不要修"的问题，  
而是"产品形态还没定型"的问题。核心判断与既有建议书一致，但本次通读额外发现三件事：

1. **建议书和路线图本身已经很成熟，但已经"落后于代码一代"** —— v1.8.0 交付了  
   定位查询、被动发现、历史后台化、零利用安全体检（四刀）、随机化 MAC 识别、  
   告警抑制，远超路线图原定的 4 项。**再写一份"补功能"的建议书价值很低**，  
   真正缺的是"把这些已经做出来的东西**讲出去**"和"把数据模型**再往前推一层**"。
2. **最大的结构性天花板仍是"快照模型"**（建议书 §5.1 已指出，尚未动工）。  
   这是唯一一条"绕不过去、且越拖越贵"的架构债。其余建议都是这条的衍生。
3. **有一个建议书遗漏的、但很现实的坑**：本项目**没有 `PRAGMA user_version` 迁移链**，  
   而 `security_findings` 竖表、`switch_map`/`port_map` 子表已经让 schema 从  
   "两张表"涨到了"五张表"。这是"资产表"改造的**前置**，不做资产表就等于在沙地上盖楼。

## 1. 现状核实（读了什么、验证了什么）

### 1.1 代码规模与结构

| 区域         | 规模                    | 说明                                                                                                                                                         |
| ---------- | --------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 根目录        | 48 个 `.py`，约 1.28 万行  | UI 用 Mixin 拆分（`main_window.py` 仍 1969 行最大）                                                                                                                 |
| `scanner/` | 19 个文件，约 5000 行       | 纯引擎层，零 Qt                                                                                                                                                  |
| `tests/`   | 71 个文件，**1673 个测试方法** | 测试:产品 ≈ 0.6:1，同类罕见                                                                                                                                         |
| 领域层 Qt 依赖  | **零**（已核实）            | `scanner/`、`history_store`、`risk_rules`、`change_detector`、`topology_discovery`、`notifier`、`scheduler`、`alert_policy`、`device_fingerprint` 全部不 import PyQt5 |

> 唯一两处 `grep "PyQt5"` 命中的是 `cli.py` 和 `scanner/aes.py` 的**文档字符串文字**，  
> 不是真实 import。结论成立：**领域层是天然的类型检查边界与 API 服务化的地基**。

### 1.2 扫描引擎（`scanner/engine.py`）

已核实的能力，全部在同类产品里属于"上游水平"：

- **Phase 编排**：`PingPhase → ArpPhase → MdnsPhase` 三阶段，新增发现方式只需登记  
  `PHASES`，编排代码不动（`DiscoveryPhase` 抽象 + `ScanContext` 共享状态）。
- **原生 ICMP**：Windows `iphlpapi.IcmpSendEcho`（ctypes，零依赖零管理员），  
  实测比子进程 ping 快约 370×；禁 Ping 主机用 `SendARP` 兜底。
- **RTT 自适应超时**：滚动窗口中位数动态夹紧 connect 超时（0.15~1.5s），局域网收敛到最短。
- **有界线程池**：端口扫描走进程内单例有界池（上限 384），避免 enrich 并发时线程爆炸。
- **规模保护**：`0.0.0.0/0` 在构建列表前就拒绝（先计数后展开），防 42.9 亿字符串撑爆进程。
- **诚实降级贯穿**：SYN/UDP 需权限就回退 connect 并写明原因；IPv6 字面量拒绝并留痕；  
  SNMPv3 优先、仅"无响应"回退 v2c、凭据错误不回退。

## 2. 真正的改进意见（按优先级排序）

以下意见**刻意避开**建议书已覆盖且已排期的项（IPv6、异步 connect、拓扑过宽折行、  
PySide6 迁移、HTTP API、互操作导出等），只讲**新的、或需要修正的**。

### P0 —— 先补 schema 迁移链（资产表的前置，当前最急）

**问题**：`history_store.py` 现在用 `CREATE TABLE IF NOT EXISTS` 建了 **5 张表**  
（`snapshots` / `devices` / `switch_map` / `port_map` / `security_findings`），  
但**没有 `PRAGMA user_version`，也没有迁移链**。文件里自己都写了注释承认：  
"给 devices 加列必须写 ALTER TABLE 迁移，`CREATE TABLE IF NOT EXISTS` 不会补列"。

**为什么这是 P0**：建议书 §5.1 的"资产表 + 观测表"改造，本质是**给现有 5 张表加列、  
建新表、双写**。没有版本号，改造时无法判断"用户手里的库是哪个年代的"，  
只能靠 try/except 猜 —— 这正是建议书自己警告的"无法安全演进"。

**做法**（半天~1 天）：

```
MIGRATIONS = [
    (1, "CREATE TABLE ... snapshots/devices ..."),
    (2, "CREATE TABLE switch_map/port_map ..."),
    (3, "CREATE TABLE security_findings ..."),
    # v2: 资产表双写
]
# 读 user_version → 顺序执行 > current 的迁移 → 写回
```

新库直接建到最新；老库自动补到最新。这比现在"靠 CREATE IF NOT EXISTS 隐式建表"可审计得多。

### P0 —— 把"零利用安全体检"和"台账"讲出去（不是代码，是采纳）

v1.8.0 做了四刀安全体检 + 定位查询 + 被动发现，但**这些价值目前只在 CHANGELOG 里**。  
建议书 §7 已经点出"README 一张图都没有"，而现状连"功能特性"章节都还没把  
`locate` / `watch` / 安全体检写全（README 的 `功能特性` 只写到 WMI，后面是  
`扫描与发现`/`识别与指纹`，v1.8 的新能力散落）。

**具体动作**（零代码，收益最高）：

- README 补一张**能力总览图**（或截图）：一屏让人看懂"这工具现在能干什么"；
- Release note 用"新增了什么"的**用户语言**写（现在是工程师语言）；
- 把 `--switch-map` / `locate` / `watch` / `--name-responder` 这些 v1.8 新 CLI 参数  
  补进 README 的命令行章节（建议书 §1.4 的落地记录里明确写了要补，需核实是否已补）。

### P1 —— 资产表 + 观测表（建议书 §4.3 / §5.1，仍是最重要的架构改造）

**这条没变，仍是"绕不过去的那条"**。v1.8 的 `query_history` 下推 + 分页是**止血**，  
没动根本。核实：`query_history` 现在仍是"捞快照行 → Python 聚合"，`device_class`  
刻意不下推（有测试钉住），说明聚合仍在应用层。`/16 × 20 快照 = 130 万行`的场景下  
这是秒级卡顿的根源。

**修正建议书的一点**：建议书把资产表推到了 v2，理由是"等 1.1/1.2 把台账用起来、需求变清楚"。  
现在 1.1/1.2 已经用起来了，**这个等待理由已经消失**。建议把资产表从 v2 提前到 **v1.9 主题**，  
因为：

- 定位查询的"历史位置"、被动发现的"在线率曲线"、变更的"长期暴露时长"，  
  都**依赖**资产表才便宜；
- 越晚做，`security_findings` 竖表里的历史事实越多，迁移成本越高。

### P1 —— 只读 HTTP API（建议书 §4.7，建议提前）

建议书把这列为 v1.9，理由是"受众是集成派，晚一轮"。但本次核实发现一个**被低估的理由**：  
**领域层已经零 Qt**，且 `cli.py` 明确写"零 GUI 依赖、可在 Windows Server Core /  
Linux / 容器运行"。也就是说，API 的**全部核心逻辑都已就绪**，差的只是一层 HTTP 接线。

**建议**：把 `ipscanner serve`（只读、默认绑 127.0.0.1）提前到 v1.9 第一项。理由：  
它是"台账"这个产品判断的**自然终点** —— 一个会自己更新的台账，如果没有 API，  
就无法被 Grafana / n8n / 自建看板消费，价值只兑现了一半。

### P2 —— 一个建议书没提的盲点：`devices` 表缺"服务"字段

建议书 §ROADMAP 的 #11 落地记录里**自己承认**了："快照表 `devices` 只存  
hostname/vendor/device_class/os_guess/open_ports，**没有服务字段**"。

这意味着：**指纹配对、变更检测、"这台设备开了什么服务"的历史对比，都拿不到服务数据**。  
`security_findings` 竖表存的是"安全事实"（TLS 到期、SMB 签名），不是"服务清单"。  
这是一个**真实的数据缺口**，会直接限制：

- 变更检测：不能报"某设备新增了 3306 端口"这种高价值变更；
- 指纹配对：随机化 MAC 设备的身份锚点更少了。

**建议**：资产表改造时，把"服务清单"作为观测表的一等字段（而不是塞进竖表）。

### P2 —— 测试规模已到临界点，建议补"覆盖率"而非"更多测试"

1673 个测试方法、0.6:1 的测试比，**继续堆测试的边际收益在下降**。建议书 §5.3 已建议  
引入 `coverage.py` 只对领域层设门禁 —— 这条仍然正确，且**现在正是时候**：  
v1.8 新增了大量领域层代码（`passive.py` / `device_fingerprint.py` / `alert_policy.py` /  
`x509.py` / `smb.py` / `llmnr_nbns.py`），但没人知道这些新代码的覆盖情况。

### P3 —— 三个"锦上添花"但值得记下的点

1. **`topology_discovery.py` 1603 行**，建议书 §5.3 已建议轻拆分（`layout.py` + `models.py`）。  
   现在比建议书测量时（1283 行）又长了 320 行，拆分理由更充分了。
2. **`main_window.py` 1969 行**，是全仓最大文件，`ui_dialogs/` 的拆分已证明 Mixin 路线可行，  
   可以照搬。
3. **CLI 参数发现性**：`cli.py` 已有 `scan/diff/history/schedule/locate/watch` 多个子命令，  
   但 `--help` 的层级和分组值得再顺一遍，让新用户 30 秒能看懂"我能干什么"。

## 3. 不建议做的（重申 + 补充，防止被误当成"没提"）

建议书 §9 的"陷阱清单"依然全部成立，这里**补充三条本次通读新看到的**：

1. **不要给领域层引入任何第三方依赖**。`requirements.txt` 只有 PyQt5 / openpyxl / xlrd，  
   这是项目最硬的护城河（手写 BER、ctypes ICMP、纯标准库 AES、手写 DER 走查）。  
   Apprise（通知聚合）这条建议书列在 v1.9，但**会破坏零依赖身份**，需要单独论证 ——  
   建议书自己也标注了这一点，别默认就上。
2. **不要为了"功能更全"去追 Nmap/SoftPerfect 的探测广度**。本项目的差异在"台账 + 自动化 +  
   可审计"，不在"多认几种设备"。建议书 §9"把一条指纹路径做到极致"的判断仍然对。
3. **不要急着把安全体检做成"CVE 扫描"**。建议书 §9 明确"绝不能给出暗示已实测可利用的  
   CVE 结论"——v1.8 的四刀是"暴露面启发式"，这条红线要守住。离线 CVE 关联（建议书 v1.9 #9）  
   即使做，也只能是"banner → CPE → 已知漏洞列表"的**参考信息**，不是"这台机器已被攻破"。

---

## 4. 一句话总结

这个项目的问题**从来不是"代码不好"**，而是：**能力已经过剩，但形态和叙事还没跟上**。  
v1.8.0 之后，最该做的三件事按顺序是：

1. **补 schema 迁移链**（半天，为资产表打地基）；
2. **把已经做出来的东西讲出去**（README/截图/Release note，零成本）；
3. **资产表 + 只读 API 提前到 v1.9**（把"会自己更新的台账"从"本地工具"变成"可集成的平台"）。

其余（IPv6、异步 connect、拓扑折行、PySide6、签名）都已在建议书里排好，  
按原计划推进即可，不必重排。
