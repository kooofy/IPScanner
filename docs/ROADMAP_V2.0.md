## 0. 重排原则（沿用 v1.9，不另立一套）

1. **一个 minor 只承载 4 项** —— 让「v2.0 交付了什么」能被一句话说清。
2. **四项各占一个不可替代的角色** —— 结构 / 出口 / 显示 / 安全网 的四分法在 v1.9
   被证明好用，v2.0 沿用同构（见 §1）。
3. **优先级不由「重要」决定，由「是否阻塞其它项」决定**。
4. **保持项目身份** —— 三条铁律继续生效：
   - **不引入第三方依赖**（Apprise #8 因此继续出局）；
   - **不开网络监听端口**（HTTP API #6、`/metrics` #7 因此让位或出局）；
   - **不装 agent、数据不出网**（多站点只做文件交换）。
5. **每一项都要能独立回滚** —— 2.1 又要动 `identity_key`，这是 `assets` 的**主键**，
   是本项目第二大的数据模型改动（第一是 1.1 本身），备份 + 双写是硬要求。

## 1. v2.0 四项

v1.9 的四分法是「结构 / 出口 / 显示 / 安全网」。v2.0 沿用同构，但主题换成
**「让台账认得出一台设备，并且让别人用得上」**：

| # | 角色 | 事项 | 优先级 | 工时 | 来源 |
|---|---|---|---|---|---|
| 2.1 | **结构** | 设备身份深化：指纹接进 `assets` 主键 | **P0（主题项）** | 5–8 天 | §3 `v1.8 #11（半）` |
| 2.2 | **出口** | 报表引擎（模板可编辑）+ 定时报表投递 | **P0** | 5–7 天 | §3 `v1.8 #10` |
| 2.3 | **入口** | 凭据配置档（按网段/组的只读账户） | **P1** | 4–6 天 | §3 `adv #6` |
| 2.4 | **可见性** | IPv6 可见性（**只做 NDP + `ff02::1` 挂靠，不做 IPv6 扫描**） | **P1** | 4–6 天 | §3 `adv #3` |

**合计 18–27 人天 ≈ 4–6 周**（建议书原文给 v2.0 的窗口是「可选」，未给工时）。

> ⚠ **与建议书 §8 v2.0 的差异见 §4** —— 建议书那份 v2.0 是「平台化」
> （PySide6 / REST API / 中心库），本文**明确不做**其中三项，理由逐条写在 §4。

## 3. v2.0 四项详情

### 2.1 设备身份深化：指纹接进 `assets` 主键（v2.0 主题项）

| 项 | 值 |
|---|---|
| 优先级 | **P0** |
| 工时 | **5–8 天** |
| 依赖 | 无（`device_fingerprint.py` 已就绪，见现状） |
| 原编号 | `ROADMAP_V1.9.md` §3 `v1.8 #11（半）` |

**为什么是它（主题项）**：v1.9 的 1.1 把 `assets.identity_key` 做成主键，但
**只认 MAC**。而现代 iOS / Android / Windows 默认开「私有 Wi-Fi 地址」——
同一台手机每次接入换一个随机 MAC。对只认 MAC 的台账，这台手机**每次扫描都是新设备**，
于是「资产总数」只增不减、变更告警全是假阳性。**这是「台账」这个定位的地基问题**，
不是锦上添花：地基歪了，2.2 的报表只是把噪声印得更漂亮。

**现状（已实测）**：

- `history_store.py:222` 的 `identity_key(mac="", ip="")` 是**唯一**的身份生成点 ——
  它同时服务于 `devices` 回填（`:319` / `:445`）与 `assets` 主键写入，改动面收敛。
- `device_fingerprint.py` **已完整实现且已成熟**：LAA 位判据、四类身份锚点 token
  （`host=` / `vendor=` / `model=` / `serial=`）、`same_device()` 四级配对规则
  （同类字段冲突**否决**；命中 `host=`/`serial=` 即同一台；`model=` 需 ≥2 token 佐证；
  只有 `vendor=` 相同**不算**）。**但全仓库 `grep fingerprint history_store.py` 为空** ——
  即：指纹机制**从未接进 `assets`**，这正是 §3 说的「延伸到主键的那一步」。
- `_ASSET_COLS`（`:244`）是「随观测刷新」的属性列；身份键不在其中。

**做法**：

- **不新开列**，在 `identity_key()` 里插入一层「指纹降级」：
  1. 有 MAC 且**非 LAA**（OUI 可查）→ 照旧用 MAC（行为不变，**老库零影响**）；
  2. 有 MAC 但**是 LAA**（随机 MAC）→ **先按指纹找已有资产**，找到就复用它的键
     （`fp:<指纹哈希>` 或原 MAC 键），找不到才新建；
  3. 无 MAC → 退回 `ip:`（现状不变）。
- 需要一个**指纹 → 已存在资产键**的查找，且必须在**同一事务**里做（否则并发扫描会各建一台）。
- **降级身份必须可解释**：资产行上要能看出「这台的身份是靠指纹认回来的」——
  否则用户看到 MAC 变了还以为数据错了（延续「不撒谎」原则）。

**验收（可写成测试）**：

- 同一台设备换 MAC（LAA）但主机名不变 → **资产数不增**，`seen_count` +1，
  `first_seen` 保持首次（这是本项的**核心断言**）；
- 两台**不同**设备、都开 LAA、主机名不同 → **仍是两台**（防「错认合并」，
  错认比漏认严重 —— 见 `device_fingerprint.py` docstring）；
- 只有 `vendor=` 相同（同厂商不同设备）→ **不算同一台**；
- 非 LAA 的普通 MAC → 行为与本项落地**前逐字节一致**（老库迁移的回归保护）；
- 老库（`identity_key` 全是 MAC/IP 形式）→ 升级后**能正常回填**，不产生重复资产。

**风险与回滚**：动主键 = 动 `assets` 的不变量。必须走 1.1 的同一套
「迁移 + 备份 + 双写」流程，且 `SCHEMA_VERSION` +1。

### 2.2 报表引擎（模板可编辑）+ 定时报表投递

| 项 | 值 |
|---|---|
| 优先级 | **P0** |
| 工时 | **5–7 天** |
| 依赖 | 2.1（报表的资产口径必须先是可信的）；`scheduler.py` ✅ 已有 |
| 原编号 | `ROADMAP_V1.9.md` §3 `v1.8 #10` |

**为什么是它**：v1.9 的 1.2（互操作导出）让资产表**给机器**用；
报表让资产表**给人**用。两者是资产表的两条出口，缺一条就仍是「自娱自乐」。
而且它的两个依赖**都已具备**（定时器 + HTML 导出），是 11 项里**前置最齐**的一件。

**现状（已实测）**：

- `scheduler.py` 已完整：`build_schtasks_create/delete/query`（Windows）、
  `build_cron_line/block`（Unix）、`build_scan_argv`、`register/unregister`。
- `excel_handler.py:234` 的 `export_html()` **已存在**，但**模板是硬编码的** ——
  表头、行着色、`<td>` 拼接全是内联 f-string，**没有**任何可替换的模板层：
  ```python
  headers = [tr("IP地址"), tr("状态"), ...]          # 硬编码
  tds.append(f'<td style="color:{color};...">{val}</td>')  # 内联拼接
  ```
  所以本项不是「加个开关」，而是**把 Markup 从代码里抽出来**变成数据。

**做法**：

- **模板外置为数据文件**（延续「声明式扩展」原则 —— 与 `oui.db` /
  `service_fingerprints.json` 同思路，**不执行代码**）：
  `assets/report_templates/*.html`，用受限占位符（如 `{{rows}}` / `{{summary}}` /
  `{{generated_at}}`）替换，**不引入 Jinja2**（第三方依赖，违反原则 4）。
- 内置 2–3 个模板（资产清单 / 变更摘要 / 暴露面摘要），用户可复制出来改。
- **CLI**：`ipscanner report --template <名> --from <快照> --to <快照> -o report.html`。
- **定时投递**：复用 `scheduler.py` 的既有能力，把「扫描 → 生成报表 → 发通知」
  串成一条链（通知用 `notifier.py`，已有）。

**验收（可写成测试）**：

- 用内置模板生成报表，**产出可解析的 HTML** 且含全部资产行（计数断言）；
- **换模板文件即换版式**：同一份数据喂两个模板，产出不同且都合法（证明模板层真的生效）；
- 语言切换下产出的**资产值**仍是规范值（`online`/`offline`），
  仅**模板文案**随语言变（i18n 铁律）；
- 定时链路：给定 argv，`build_task_command` 产出与 2.2 前**逐字节一致**
  （不破坏既有定时）—— 投递是**新增**一个定时任务类型，不是改旧的。

### 2.3 凭据配置档（按网段/组的只读账户）

| 项 | 值 |
|---|---|
| 优先级 | **P1** |
| 工时 | **4–6 天** |
| 依赖 | 无（但要动配置模型，见下） |
| 原编号 | `ROADMAP_V1.9.md` §3 `adv #6` |

**为什么是它**：现在 SNMP 团体字 / WMI 账户是**全局单一值**。真实企业里不同网段
属于不同团队、用不同只读账户 —— 全局值意味着要么全用同一个（不合规），
要么每次手改（易错）。把它变成**带作用域的一组对象**，是「能进真实环境」的门槛。

**现状（已实测）**：

- 凭据散落为参数：`scanner/snmp.py:241` 的 `snmp_walk(..., community="public")`、
  `switch_mapper.py:81` 的 `map_switch_ports(ip, community="public", ...)` ——
  **默认值硬编码 `"public"`**，且**没有**任何「按目标选择凭据」的层。
- SNMPv3 口令已走环境变量（`scanner/snmp_v3.py`），是**单套**全局值，无作用域。
- **没有** `credentials.py` 之类的模块（`grep credential` 在非测试代码里为空）。

**做法**：

- 新增零依赖的 `credentials.py`：一个**凭据档** = `{作用域(网段/CIDR 列表),
  协议(SNMP v1/v2c/v3 | WMI), 账户/团体字}` 的列表；提供
  `for_target(ip) -> Credential | None` 的**最长前缀匹配**选择。
- 敏感值**继续走 `env:VAR` 间接引用**（沿用 `notifier.py` 的既有约定，
  与 CLI SNMPv3 口令「只走环境变量」一致），**绝不**把明文写进配置文件。
- 扫描时按目标 IP 选档；**选不到就明确报「该目标无可用凭据」**，
  而不是静默回落 `public`（后者会让用户以为扫过了）。

**验收（可写成测试）**：

- `for_target()` 的最长前缀匹配：`10.1.0.0/16` 与 `10.1.2.0/24` 并存时，
  `10.1.2.5` 命中后者（更具体优先）；
- 无匹配 → 返回 `None`，**不回落 `public`**；
- `env:VAR` 间接引用能正确解析，且配置文件里**不含**明文口令
  （扫描配置文件文本断言）；
- 单档配置下行为与现状**逐字节一致**（老用户零感知）。

### 2.4 IPv6 可见性（只做 NDP + `ff02::1` 挂靠）

| 项 | 值 |
|---|---|
| 优先级 | **P1** |
| 工时 | **4–6 天** |
| 依赖 | 无 |
| 原编号 | `ROADMAP_V1.9.md` §3 `adv #3` |

**为什么是它**：现代网络里手机/Windows 默认有 IPv6 地址。只看 IPv4 会漏掉
「只有 IPv6 的设备」。但**完整的 IPv6 资产盘点在语义上不成立**（一个 /64 有
2⁶⁴ 个地址）—— 建议书 §9 明说「**只做可见性**，挂在已有 IPv4 资产上」。

**现状（已实测）—— ⚠ 这项的前提比看起来紧**：

- IPv6 在本项目是**被显式拒绝**的，不是「未实现」：
  - `scanner/range.py:15` 模块 docstring 写明「**刻意显式拒绝** IPv6 字面量」，
    `:107` 提供 `is_ipv6_range()` 只为把「暂不支持」和「格式写错」分开提示；
  - `scanner/engine.py:200-206` 遇到 IPv6 范围会**跳过并提示**
    「本工具目前只支持 IPv4 扫描」。
  - 这个决定是**对的**（下游 ARP/NetBIOS/WMI/SNMP 全假设 IPv4）——
    本项**不推翻它**。
- `scanner/passive.py:56` 只把 IPv6 组播 MAC 前缀当作「不是单台设备」的黑名单，
  **没有任何** NDP / `ff02::1` / mDNS-over-v6 的读取代码。

**做法（严格限定在「可见性」）**：

- **不做** IPv6 地址扫描。只做**读取**：
  1. 本机 **NDP/邻居缓存**整表 dump（对应 IPv4 的 ARP 表 dump，零发包）；
  2. **`ff02::1` 多播**一次 ICMPv6 echo（等价于 IPv4 的 `ff02::1` ping），
     促使设备回一个邻居通告，再读缓存 —— **这不遍历地址空间**；
  3. **mDNS over IPv6** 监听（复用现有 mDNS 路径）。
- 拿到的 IPv6 地址**挂到已有 IPv4 资产上**（用 2.1 的指纹 / MAC / 主机名关联），
  **不新建**「IPv6-only 资产」这种一等实体 —— 与本项边界一致。
- 明确提示：本项产出的是「**可见性**」，不是「**IPv6 资产清单**」。

**验收（可写成测试）**：

- `parse_ndp_cache()` 对 Windows（`netsh interface ipv6 show neighbors`）、
  Linux（`ip -6 neigh`）、macOS（`ndp -an`）三种输出各喂样本 → 解析正确
  （**纯函数、可单测**，零网络）；
- 关联逻辑：给定一台已有 IPv4 资产 + 一个 MAC 一致的 IPv6 邻居 → **并入同一行**，
  不新增资产；
- 无 IPv6 环境的机器 → **优雅降级**（提示「本机未启用 IPv6」），不报错、不崩；
- **不发多余包**：断言除 `ff02::1` 单次多播外无其它出站（与被动发现同口径）。

## 4. 与建议书 §8 v2.0 的差异（我改了什么、为什么）

建议书 §8 的 v2.0 是「**平台化**」（5 项）。本文**只采纳其中 1 项**，明确不做 4 项：

| 建议书 v2.0 项 | 本文裁定 | 理由 |
|---|---|---|
| 1. PySide6 迁移（LGPL + Qt6） | **不做（暂无必要）** | 迁移是**大范围机械改动**，收益是许可证与 Qt6，而本项目当前**无许可证压力**（PyQt5 GPL 用途成立）。1116+ 测试是资产，不该为「更现代」付全量回归风险 —— 留到真有 Qt6 独占需求时再议 |
| 2. REST API 完整版 + 只读 Web 看板 | **不做** | 违反原则 4（开监听端口）。**与 §2 对 #6 的裁定一致** |
| 3. 报告引擎（模板可编辑） | **采纳 → 本文 2.2** | 唯一一条不开端口、不加依赖、且依赖已齐的 |
| 4. 多站点：快照导入/导出协议 + 可选中心库 | **不做（本组最该做，但仍不做）** | ⚠ 见下 |
| 5. MCP/LLM 只读查询层 | **不做** | 属「只读暴露」的另一种形态，但它需要一个**常驻查询接口**才能被外部调用；若纯文件式则已被 1.2 覆盖 |

**关于第 4 项（多站点）为什么忍住不做**：它的方向完全正确（文件交换、不装 agent、
不碰云端），但**前置不在编码侧** —— 当前 `history_store.py` 只有
**`save_snapshot()`（`:417`）**，**没有** `export_snapshot()` / `import_snapshot()`。
要谈「多站点快照交换」，得先定义**一份可交换的快照格式**（含 schema 版本、
身份键、冲突解决）—— 那是一份**协议设计**，不是一周的活。**先把它作为 §5 的未决项立项。**

---

## 5. 未决项（不排期，但记在案）

1. **离线 CVE 数据快照的维护模型**（`adv #9` 的前置）：
   谁生成？多久更新一次？离线包放哪、怎么验签？—— **产品决策**，答不上来之前不编码。
2. **多站点快照交换协议**（建议书 v2.0 #4 的前置）：
   一份快照的**可交换格式**长什么样？跨站点的 `identity_key` 会不会冲突？
   —— 需要一份独立的**协议草案**，早于任何实现。
3. **Nagios 插件契约**（`adv #7` 里唯一不违反原则的部分）：
   一次性执行、用退出码表达状态。**适合补丁轨道**单列，不必占 v2.0 名额。

## 6. 建议的落地顺序

```
2.1 身份深化（P0，主题项）
 └─ 先做，因为 2.2 报表的「资产口径可信」由它保证；
    它动主键，越早落地越早暴露问题。

2.2 报表引擎（P0，出口）
 └─ 依赖 2.1 的口径；依赖已齐（scheduler + export_html），
    可与 2.1 后半段并行（模板层独立于身份层）。

2.3 凭据配置档（P1）   ┐
2.4 IPv6 可见性（P1）  ┘ 彼此独立、都与 2.1/2.2 无耦合 → 可并行或穿插。
```

**里程碑**：2.1 + 2.2 完成 = 可发 **v2.0**；2.3 + 2.4 = **v2.1**（或并进 v2.0 若提前）。
补丁轨道（§5 未决项 3 之类）始终可承接「与主题无关、能独立验收」的小项。
