## 2. 勘误一：§1.1 规模表是建议书（v1.7.6）的旧数

### 2.1 原文与实测

**原文**（`docs/CODE_ANALYSIS_V1.8.md` §1.1）：

| 区域 | 规模 |
|---|---|
| 根目录 | 48 个 `.py`，约 1.28 万行 |
| `scanner/` | 19 个文件，约 5000 行 |
| `tests/` | 71 个文件，1673 个测试方法（测试:产品 ≈ 0.6:1） |

**`PRODUCT_ADVISORY.md` §1.1（v1.7.6 基线，`[实测]` 非空行）**：

| 区域 | 文件数 | 行数 |
|---|---|---|
| 根目录 | **48** | **12 772** |
| `scanner/` | **19** | **5 057** |
| `ui_dialogs/` | 9 | 1 796 |
| `tests/` | 58 | 11 772 |

测试 : 产品代码 ≈ **0.6 : 1**，共 **1116 个用例**。

**本仓库实测 @ `51e5036`（v1.8.0，非空行）**：

| 区域 | 文件数 | 非空行 |
|---|---|---|
| 根目录 | **51** | **15 126** |
| `scanner/` | **23** | **6 340** |
| `ui_dialogs/` | 10 | 2 094 |
| `tests/` | 71 | 17 592（1673 个测试方法） |

测试 : 产品代码 = 17 592 / (15 126 + 6 340 + 2 094) = **0.75 : 1**。

**结论**：文档 §1.1 的 `48 / 约 1.28 万`、`19 / 约 5000`、`0.6:1` **三个数字全部来自
建议书 §1.1（v1.7.6）**，没有重算；它**丢掉**了建议书的 `ui_dialogs/` 行；
只有 `tests/` 的文件数与方法数（71 / 1673）是当前的。

> **为什么能确定是"抄"而不是"碰巧算成一样"**：`约 1.28 万` 对应建议书的 `12 772`，
> `约 5000` 对应 `5 057` —— 两个都是**四位有效数字级别的吻合**，而当前真值是
> 15 126 与 6 340。四舍五入到"万/千"也不可能从 15126 得到 1.28 万。

### 2.2 口径不一致（同一张表里）

| 行 | 口径 | 值 |
|---|---|---|
| 根目录 / `scanner/` | 建议书的**非空行**（v1.7.6） | 12 772 / 5 057 |
| `main_window.py` | **`wc -l` 总行**（当前） | 1969 |
| `topology_discovery.py` | **`wc -l` 总行**（当前） | 1603 |

同一张表里两种口径、两个版本。`main_window.py` 的当前**非空**行数是 **1741**
（建议书时 1676），文档写的 1969 是总行数。

### 2.3 影响

- §1.1 是**全文档唯一自称「已核实」的统计表**，它的数字会被后来者当基线引用
  （建议书 §1.1 就是这么被引用的）。**这一节必须先重算再引用。**

- **不影响** §2 的技术判断 —— 那些我逐条核过（§1 表 #7~#12），全部属实。

## 3. 勘误二：`user_version` 不是「建议书遗漏的坑」

### 3.1 原文

文档把这件事当成**头号新发现**，在 §0 结论先行第 3 条与 §2 的 P0 各写了一次：

> 3. **有一个建议书遗漏的、但很现实的坑**：本项目**没有 `PRAGMA user_version` 迁移链**…

### 3.2 实测

`grep -n user_version docs/PRODUCT_ADVISORY.md docs/ROADMAP_V1.8.md` —— **建议书里出现 4 次**：

| 位置 | 原文 |
|---|---|
| `PRODUCT_ADVISORY.md:233` | 「给 `devices` 表加 `PRAGMA user_version` 与迁移链（现在是 `CREATE TABLE IF NOT EXISTS`…）」 |
| `PRODUCT_ADVISORY.md:239` | 排期表里的一行：`| user_version + 迁移链 | P1 |` |
| `PRODUCT_ADVISORY.md:312` | 「加一个版本号 + 顺序迁移列表（**`MIGRATIONS = [(1, sql1), (2, sql2), ...]`**）」 |
| `PRODUCT_ADVISORY.md:475` | 建议书自己的第 **12** 条 |
| `ROADMAP_V1.8.md:334` | §3 #12：`| user_version + 覆盖率 / pyright / pip-audit + BER fuzz | **拆分** | BER fuzz、**`user_version` 进补丁轨道**；质量门禁进 v1.9 |` |

**连代码骨架都一样**：文档 §2 给的
`MIGRATIONS = [(1, "CREATE TABLE ... snapshots/devices ..."), (2, ...), (3, ...)]`
与建议书 §312 的 `MIGRATIONS = [(1, sql1), (2, sql2), ...]` 是同一个设计。

### 3.3 影响：性质从「新点子」变成「欠账」

**真正的问题不是"没人想到"，而是"排了期、然后被静默漏掉"**：

- 路线图 §3 #12 已把 `user_version` 明确指派给**补丁轨道**；
- 而路线图 §6 报「**补丁轨道 8 件已结**」—— 那 8 件是建议书 §10 的清单，
  **`#12` 是 §3 里另一行**，不在这 8 件之内，因此"已结"这个说法**掩盖了它从未执行**。

这个区别很实际：**「新点子」会在排期会上被讨论要不要做；「欠账」必须被追平**，
否则路线图的"已完成"计数就是失真的。`user_version` 应改写为「§3 #12 已排期未执行」
再进排期表。

> 文档的技术结论（该补迁移链）**完全正确**，本文不反对；反对的只是它的**定性**。

## 4. 口径 / 措辞需修正（非事实错误）

### 4.1 `topology_discovery.py` 的「+320 行」是跨口径相减

| | 建议书 §5.3 | 文档 §2 P3-1 | 同口径实测 |
|---|---|---|---|
| 口径 | **非空行** | `wc -l` | **非空行** |
| 值 | 1 283 | 1 603 | **1 361** |
| 增量 | — | 1 603 − 1 283 = **+320** | 1 361 − 1 283 = **+78** |

`wc -l` 下 v1.7.6 是 1 509、现在是 1 603（+94）。**三种口径三个数**，
文档挑了一个**最显眼**的组合。

**结论仍成立**（它确实是第二大文件、确实值得拆），但"**+320 行，拆分理由更充分了**"
这个论证被夸大了约 **4 倍**（真实 +78 非空行）。要论证拆分，用"它是第二大文件、
1361 非空行"比用增长率更有力。

### 4.2 README 的 CLI 参数**已经补了**

文档 §2 P0-2 写：

> 把 `--switch-map` / `locate` / `watch` / `--name-responder` 这些 v1.8 新 CLI 参数
> 补进 README 的命令行章节（建议书 §1.4 的落地记录里明确写了要补，**需核实是否已补**）

**核实结果：四个都已在** `README.md` 的「命令行（无头模式）」章节（全文命中
`locate` 5 次 / `watch` 8 次 / `switch-map` 1 次 / `name-responder` 1 次），
退出码表也已补 `4`（`locate` 未定位到）。

**真正没做的比它说的更窄、也更具体**：

| 检查 | 结果 |
|---|---|
| 「定位查询」在 README 出现 | **0 次** |
| 「被动发现」在「功能特性」段（74–192 行）出现 | **0 次** |
| README 截图 / 示意图 | **0 张**（3 个 `![]` 全是 shields.io 徽章） |

即：**两个 v1.8 头牌能力只活在 CLI 示例里，功能特性列表里根本没有。**
所以该做的是「把两个头牌写进功能特性 + 加一张截图」，而不是"补 CLI 参数"。

### 4.3 `requirements.txt` 漏列两个同族包

文档 §3-1：「`requirements.txt` **只有** PyQt5 / openpyxl / xlrd」。
实测还含 `PyQt5-Qt5`（按平台分流的两行）与 `PyQt5_sip==12.18.0`。

**它要论证的结论（零第三方依赖是护城河）成立** —— 那三个都是 Qt 同族、不是独立第三方。
只是"只有三个包"的措辞会让人以为 Qt 只需一个依赖。

## 5. 核过属实的技术判断（可直接采纳）

以下是我逐条核实**成立**的，不因上面的勘误而贬值：

4. **`query_history` 的 `device_class` 刻意不下推** —— 属实，`history_store.py:825`

## 6. 本次复核补充的一条（原文未提）

文档 §2 P2 说「`devices` 表缺服务字段」是数据缺口 —— **对，但它比文档以为的便宜得多**：

- `ScanResult.services` / `service_details` **内存里本来就有**
  （`scanner/models.py:23`、`:35`）；
- 而 `history_store.py` **全文没有 `services`** —— 快照只写 `open_ports`。

即：**服务数据是"采集了、然后在库门口扔掉"，不是"没采集"。**
所以文档 §2 P2 说它"直接限制变更检测（报不出『某设备新增了 3306 端口』）"
—— 症状描述正确，但**补上它不需要任何新增探测**，只是把手里已有的数据落库。
这个区别会影响排期判断（它比"加一个采集器"轻得多）。

## 7. 未复核范围与结论

### 7.1 本次未复核的部分（诚实声明）

- **它的产品判断**：资产表提前到 v1.9、只读 API 提前到 v1.9 第一项、
  "能力过剩但叙事没跟上"、§3 三条"不建议做的"。这些是**观点**，不是可证伪的事实。
  本文只确认它们**所依赖的事实前提**成立（§5 第 1、5 条），不评价排序本身。
- **它引用的建议书内容**是否忠实（我只核了 `user_version` 那一处，发现了 §3 的问题）。
- **`1673 个测试方法 → 边际收益下降`** 这个判断：数字属实，但"该补覆盖率而非更多测试"
  属建议，本文不评。

### 7.2 结论

**这份文档应当被当作"线索来源"，不应被当作"待办清单"直接执行。**

| 用途 | 判断 |
|---|---|
| 拿它的**技术判断**（资产表、API、README 叙事） | ✅ 可采纳 —— §5 那几条我核过，前提成立 |
| 拿它的**统计数字**当基线 | ❌ 不可 —— §1.1 有三个数字是 v1.7.6 的旧数 |
| 拿它的**"新发现"**当新需求 | ❌ 不可 —— 头号 P0 是建议书 #12 的**欠账**，不是新点子 |
| 引用它时 | 先按 §2.1 重算 §1.1，并把 `user_version` 改写成"已排期未执行" |

**一句话**：它的**眼睛很准**（依赖扫描、schema、函数行为全部属实），
但它的**尺子没校准**（规模表抄了旧数、增长率跨口径相减、把欠账当新发现）。
这两件事必须分开对待 —— 前者直接采纳，后者重算后再引用。
