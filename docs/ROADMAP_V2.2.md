## 0. 重排原则（继续沿用 v1.8 / v1.9 / v2.0 / v2.1，不另立一套）

1. **一个 minor 只承载 4 项** —— 让「v2.2 交付了什么」能被一句话说清。
2. **四项各占一个不可替代的角色** ——「结构 / 出口 / 显示 / 安全网」四分法连着四轮好用，  
   但**这一轮我建议改成「主题项 + 三项支撑」**，理由见 §1。
3. **优先级不由「重要」决定，由「是否阻塞其它项」决定**。
4. **保持项目身份** —— 三条铁律继续生效，**这一轮尤其吃紧**（见 §0 尾注）：
   - **不引入第三方依赖**；
   - **不开网络监听端口**；
   - **不装 agent、数据不出网**。
5. **每一项都要能独立回滚**，且**只做能独立验收的**（v2.1 新增的自约束，继续生效）。

> ⚠ **v2.2 的新特点：候选池里"最想要的那几项"全部撞上身份边界。**  
> CVE 在线更新（要联网）、HTTP API（要开端口）、Apprise（要加依赖）、  
> Prometheus（要常驻）—— 每一条都踩在 §0 原则 4 上。  
> 所以本轮的关键不是「挑最想要的功能」，而是  
> **「哪些需求可以在不破边界的前提下被满足」** —— 这正是 §2 候选池的筛选依据。

## 1. 主题：**已定 A「能取信」**（决策记录）

v1.9「规模与身份」、v2.0「平台化」、v2.1「看得更深」——每轮都有一个能一句话说清的主题。  
v2.2 的候选有三个，**方向不同、代价不同**。**用户已拍板选 A**，以下是记录（含选择依据与
被放弃的两条及其去向），供后续复查。

### 1.1 已选定：主题 A：「**能取信**」—— 供应链与可信度

> 一句话：**让用户和企业敢装、敢分发、敢写进采购清单。**

- **要解决的痛**：`P2-13` 无代码签名 → SmartScreen / 杀软误报（PyInstaller + 原始套接字 +
  `net view` + WMI 是 EDR 高敏组合）。这不是"功能缺失"，是**装机第一步就劝退**。
- **内含的工作**：`winget` / `scoop` 清单、Release 正文结构化、`pip-audit` 门禁补齐与 SBOM。
  ⚠️ **代码签名本身已决定不做**（见 §1.4），故本条不含签名流水线。
- **代价**：**全部是"一个 manifest / 一段 CI"级的活**，无外部审批依赖。
- **风险**：低。唯一实质缺口是**签名仍未解决**（P2-13 保持"未修"），
  缓解靠 README 引导话术（现状做法）。

**选它的理由**（三条，按重要性排序）：

1. **A 是唯一"不做就一直流血"的**：B 和 C 晚一轮做，损失是"少一个功能"；
   A 晚一轮做，损失是**每一个新用户的第一印象**（SmartScreen 拦截 → 用户直接放弃）。
   建议书 §5.4 的原话说得最准：*"新版 SmartScreen 的信誉按同一个签名身份持续发布累积 ——
   拖一年，就等于晚一年开始攒信誉。"*
2. **A 不占车道**：它的活全是轻量的，可以**与其它三项并行**推进，不挤占 3.2/3.3/3.4 的排期。
3. **B 是纯赚**：它没有对外依赖、没有审批、没有风险，可以直接作为"结构项"落地（即 3.2）。

### 1.2 未选：主题 B：「**能接进**」—— 声明式扩展与文件交换

> 一句话：**让用户不改代码就能把工具接进自己的环境。**

- **要解决的痛**：工具能力目前"焊死在代码里"——端口→服务映射、扫描目标、报表结构
  都只有内置一份；用户想按行业（工控 / 医疗）调整，只能改代码。
- **内含的工作**：把 `COMMON_PORTS` / `_PORT_NAME_TEXT` 做成与 `service_fingerprints.json`
  同构的外置数据；`-iL targets.txt`（nmap 习惯）目标文件；补 `--format` 式自定义输出模板。
- **代价**：**性价比最高的主题**，全是"几天"级，且完全贴合现有架构（已有三处同构先例）。
- **风险**：天花板不高 —— 是"更好用"，不是"能做新事"。
- **去向**：**其"结构项"那一半已被收进 3.2**（端口映射外置 + `-iL`）——
  等于 v2.2 实收了主题 B 的精华，只是不把它当主题。

### 1.3 未选：主题 C：「**能说清**」—— 网络行为的自我解释

> 一句话：**让工具能回答"我刚刚看到的是什么、它意味着什么"。**

- **要解决的痛**：已有大量事实（TLS 证书、SMB 方言、LLMNR 响应器、CVE 候选、
  无线拥塞、端口利用率），但**用户拿到一串事实后仍然不知道"所以我该做什么"**。
- **内含的工作**：CVE 数据的新鲜度自解释（在线更新）、风险结论的"下一步动作"建议、
  资产变更的可解释性、审计日志的自查视图（"过去 24h 我向哪些网段发了多少包"）。
- **代价**：中等，但**每一项都要小心不越过"不给可利用结论"的红线**。
- **风险**：容易做成"多加几行说明文字"的虚功。
- **去向**：**其两项已被收进 v2.2** —— CVE 数据新鲜度自解释 = **3.1**（且升为主题项）、
  审计自查视图 = **3.3**。**C 的实质内容比 A 进得更多**，只是同样没拿到主题名。

### 1.4 🔴 用户决定（2026-10-14）：**启动 SignPath 申请**（推翻当日早先的「不启动」）

**决定**：**启动 SignPath Foundation 申请**（原 3.1 方案的申请部分），
并把 `P2-13`（无代码签名）从「未修」改为**「申请中」**。

> 🔴 **同日两次相反的决定，必须写清是哪一次生效**：
> 同日早些时候用户先说「不启动 SignPath 申请」（当时据此把 3.1 降级、主题位让给
> CVE 在线更新）；**随后用户改主意「要 signpath.org 申请」**。
> **以最后一次为准：启动申请。** 早先那次决定的连带后果保留在下方「已作废但保留记账」，
> 以免两个版本在仓库里互相矛盾。

**连带后果（三条）**：

1. **v2.2 的四项交付范围不变**。申请本身是**外部等待过程**，不占开发名额 ——
   它既不新增也不删除 §3 里的任何一项，只是给 `P2-13` 挂上「申请中」。
2. **获批后才有新工作**：签名流水线接线（`release.yml` 在
   「构建 CLI 版」与「打包分发产物」之间插入签名步骤）。这笔账**不进 v2.2 §3**，
   因为审批周期不可预期；何时接线看审批结果。
3. **`Reputation` 一栏仍然偏弱**（仓库公开才 4 天、stars/下载为 0），
   审核方**可能**追问使用量。已定的应对是如实回复 + 继续积累，见
   `docs/SIGNPATH_APPLICATION.md` §3.1。

**已作废但保留记账（2026-10-14 当日早先的「不启动」）**：

- 原判断：摘掉签名后，剩下的 `winget`/`scoop` 清单 + SBOM + Release 结构化
  **撑不起「主题项」的分量**，故原 3.1「可信分发」降级为补丁轨道（见 §3.4.1）、
  主题位由 3.1「CVE 快照在线更新」顶上。
- 该降级**不回滚**：CVE 在线更新已作为 v2.2 主题项开工并落地（见 §9）。
  重启的是「申请」这个动作，不是把「可信分发」重新提回主题位。

  prune 上限 1000 行。端口维度改记**规模**：`ports_scanned`（本次扫了多少个端口，
  22 / 1023 / 65535 恰好区分 quick / standard / all）+ 由它算出的发包估算。
  这已经能回答自查真正要问的问题「**我这次发了多少探测**」。
  ⇒ 若将来确实需要逐端口直方图，正确做法是**另建一张汇总表**（端口数 × 扫描数
  的稀疏表），而不是往审计行里塞清单。

**测试**：`tests/test_audit_activity.py` 29 例 —— 交叉验证（聚合 == 手工按行算）、

#### 落地记录（3.4-a ~ 3.4-d，2026-10-15）

**3.4-a Nagios 插件契约 —— ✅ 新增 `nagios_check.py` + CLI `nagios`**

- 一次性执行、单行输出（`STATUS - 说明 | perfdata`）、退出码
  **0/1/2/3 = OK/WARNING/CRITICAL/UNKNOWN** —— 不常驻、不开端口、不装 agent、
  零第三方，三条铁律一条不破（裁定见 `ROADMAP_V2.1.md` §3 adv #7）。
- 数据源只有本机历史快照库：把**最近两次快照**喂给 `change_detector.detect_changes()`。
  规则：新增设备 ≥ `--warn-new`（默认 1）→ WARNING，≥ `--crit-new`（默认 5）→
  CRITICAL；身份变动（MAC 变更 / 随机 MAC）≥ `--warn-identity`（默认 1）/
  `--crit-identity`（默认 3）同理。
- 🔴 **数据不可信时报 UNKNOWN，绝不猜成 OK**：没有快照 / 最近快照超过
  `--max-age-hours`（默认 24）→ UNKNOWN(3) + 下一步动作。
  ⚠️ **只有一次快照时**报 OK + 说明「尚无基线」而不是 UNKNOWN —— 新部署一上线
  就告警是噪声；但也**不编造**「新增 0 台」。
- ⚠️ **消失设备只计数不告警**（perfdata 里给 `'gone'`）：快照间隔 + ARP 过期会让
  「没扫到」看起来像「设备没了」（与 `watch` 的立场一致）。
- 🔴 **本子命令的退出码是 Nagios 语义**，与其它子命令的 0/1/2/3（成功/错误/
  有变更/环境错）**不同** —— 这是插件规范的硬要求，不能两全，所以独立子命令、
  既有语义一个字没动（`cmd_diff` 的 `EXIT_CHANGES=2` 仍是「有变更」）。
- 🔴 **插件行一律 ASCII 英文**：这行是给监控系统解析、告警短信携带的，非 ASCII
  在部分 NMS / 短信网关会乱码或被截断；`OK/WARNING/CRITICAL/UNKNOWN` 本身也是
  规范固定词。与 CLI 其它子命令的中文输出**有意不同**（人读的报告走
  `--format json` 或 GUI）。
- 测试：`tests/test_nagios_check.py` 18 例 —— 四态齐全、阈值可配、身份变动告警、
  消失不告警、perfdata 分号位正确（含 `age` 的 `s` 单位）、**插件行单行纯 ASCII**、
  CLI 退出码 == 插件退出码。

**3.4-b `excel_handler` 导出提示语本地化 —— ✅**
