## 0. 重排原则

1. **一个 minor 只承载 4 项** —— 让「v1.9 交付了什么」能被一句话说清。
2. **四项各占一个不可替代的角色**：
   - ① **结构**（动数据模型）—— **资产表 + 观测表**；
   - ② **出口**（让结构产生对外价值）—— **互操作导出包**；
   - ③ **显示**（数据齐了但画不下）—— **拓扑可读性包**；
   - ④ **安全网**（让这次大改可回滚）—— **质量门禁**。
3. **优先级不由「重要」决定，由「是否阻塞其它项」决定** —— 资产表本身用户看不见，
   但**报表、导出、趋势类功能全都要先读它**，所以它是 P0 主题项。
4. **保持项目身份** ——
   - 不引入第三方依赖 → 通知渠道 **#8 Apprise 继续出局**；
   - **不开网络监听端口** → 只读 HTTP API（#6）让位给**文件型导出**（1.2）。
5. **每一项都要能独立回滚** —— 1.1 是本项目**历史上最大的一次数据模型改动**，
   双写 + 老库备份是硬要求（建议书 §5.1 的原话），不是可选项。

## 1. v1.9 四项

### 1.1 资产表 + 观测表（v1.9 主题项）

| 项 | 值 |
|---|---|
| 优先级 | **P0**（v1.9 主题项） |
| 工时 | **8–12 天** |
| 依赖 | `user_version` 迁移链 ✅ **已就绪**（1.8.0 之后已落地） |
| 原编号 | 建议书 v1.9 #1；详见建议书 §4.3 / §5.1 |

**为什么是它**：现在「台账」不是一个**东西**，而是「最后一份快照」的别名。三处硬证据：

- `devices` 表**没有** `first_seen` / `last_seen` 列 —— 首见/末见时间是
  `query_history()` 靠**按快照时间升序遍历 + 内存聚合**推导出来的
  （`history_store.py:837` 的说明就是这么写的）；
- `port_map` 与 `security_findings` 都**以 `snapshot_id` 为维度**，
  所以「这个端口接了几台设备」「Telnet 开了多久」都要**把 N 份快照读一遍**才算得出来；
- 后果：趋势类问题（在线率曲线、首次出现告警、**端口长期暴露时长**、MTBF/抖动）
  现在要么做不到，要么贵到不敢放进交互路径。

**现状（已实测，2026-10-11 复核）**：

- 五张表 `snapshots` / `devices` / `switch_map` / `port_map` / `security_findings`，
  **全部以快照为维度**。`devices` 的一行 = 「**某快照里的**某台设备」，
  不是「一台设备」—— 同一台机器扫 3 次就有 3 行。
- `devices` 已有 `location` / `user` / `remark` 三列（Excel 匹配字段）——
  资产表要的「人工维护字段」**雏形已经在**，不用新造概念。
  ⚠ 但它们在 `devices` 上意味着**每次快照都重存一遍**：改一次备注要改 N 行。
- ⚠ **`devices` 不存服务**：`scanner/models.py:23` 的 `services` 与 `:35` 的
  `service_details` 在内存里是齐的，但 `history_store.py` **一次都没写过它们**
  （全文件 **0 处**引用）—— 服务是「采集到、在数据库门口丢掉」。
  **推论（对工时是好消息）**：资产表要补服务清单，**不需要新增任何探测**，
  只需补一次写入。
- 迁移链已就绪：`user_version` + `MIGRATIONS` 已在 1.8.0 之后落地
  （`db_util.apply_migrations()`，`SCHEMA_VERSION = 3`，含**老库版本推断**）。
  **资产表就是第 4 版迁移** —— 这也是「为什么现在能做、以前不能」的直接答案。

**做法**：

> ⚠ 下面这段是**原方案**；落地时按实测改了三处，改完的版本见 §「落地记录」。
> 留原文是为了让"为什么改"看得见 —— 三处都是写方案时没回源码核的「现状」错误。

- **新增两张表**：
  - `assets`（一行 = **一台设备**）：`identity_key`（MAC 归一化后大写）、
    `first_seen` / `last_seen` / `seen_count`、当前 ip/hostname/vendor/device_class/
    os_guess、`location` / `user` / `remark`、`custom_json`；
  - `asset_observations`（一行 = 一台设备在**某快照**的一次观测）：
    保留 `snapshot_id` 外键 + `CASCADE`，装 `ip` / `status` / `open_ports` /
    服务清单 / `risk_score`。
  - `snapshots` 表**语义不动** —— 快照是用户能理解的心智模型
    （「10 月 9 日那份清单」），资产表是**实现**（建议书 §5.1 第 3 条）。
- **迁移 v4**：**不用 `IF NOT EXISTS`**。迁移链的规矩是「第 4 版起结构不符要报错，
  不要静默跳过」（见 `history_store.py` 头部注释）。
- **双写**（建议书 §5.1 的硬要求）：`save_snapshot()` 照旧写 `devices`，
  **同时**写 `assets` / `asset_observations`；读路径**逐步**切换，
  `query_history()` 全程保持可用。
- **老库自动升级 + 保留备份文件**：升级前把库文件复制一份（带版本号后缀），
  失败可整体回退。
- **回填**：升级老库时把已有快照**一次性**折进 `assets`，
  否则老用户升级后资产表是空的、等于没升。
- **`identity_key` 只认 MAC**：随机化 MAC 的**降级身份**接进主键是另一件事
  （见 §3），本项不动 `#11` 已有的指纹机制。

**验收（可写成测试）**：

- 升级一个**已有 3 份快照的老库** → `assets` 行数 = 去重后的**身份键**数；
  且 `first_seen` / `last_seen` 与 `query_history()` 的结果**逐台一致**
  （这是回填正确性的**唯一**硬标准）；
- 同一台设备连扫 3 次 → `assets.seen_count == 3`，`asset_observations` 3 行；
- **双写一致性**：一次 `save_snapshot()` 后，`devices` 与 `asset_observations`
  对同一 `(snapshot_id, ip)` 的 `status` / `open_ports` 一致；
- **可回滚**：升级前的库文件被备份，且备份文件能被**旧版本程序**打开
  （`user_version` 仍是旧值、表结构未被改写）；
- **读路径切换不改变对外行为**：老库升级后 `locate_device()` /
  `device_timeline()` / `query_history()` 结果与升级前**逐字段相同**。

**落地记录（2026-10-12，第 ①+②+③ 刀完成）**

第③刀（读路径）补的是「读」：新增 `list_assets()` / `get_asset()` / `asset_count()`
直接读 `assets` 表（一行一台设备、按 identity_key 去重），并接 `cli assets` 子命令作为
第一个消费方。现有三个读函数（`query_history` / `locate_device` / `device_timeline`）
**保持只读 `devices`**，满足「逐字段相同」验收；资产表缺失的旧库（v4 前）优雅降级为空。

实测之前写错的三处「现状」，逐条改掉：

| 原方案 | 实测 | 改为 |
|---|---|---|
| `identity_key` = MAC 归一化后**大写** | 仓库里两处 `normalize_mac()`（`alert_policy` / `excel_handler`）**都是小写** | **小写**，复用 `alert_policy.normalize_mac()`（不再造第三份） |
| 另建 `asset_observations` | `devices` **本身就是**「每快照一条观测」的表，再建一张等于整表复制（/16 × 20 快照是百万行级） | **不建**。改为给 `devices` 加 `identity_key` 列 —— 观测维度复用原表 |
| 观测里装 `risk_score` | 产品代码里 **0 处** `risk_score`（风险是 `risk_rules.score_risk()` 按需算的，不落库） | 去掉。`custom_json` 同理去掉（无人写入，需要时再加一列） |

另外三处**设计**调整（不是笔误，是落地时才想清楚的）：

- **切片 ① 与 ② 合并**。原计划 ① 只做「迁移 + 建表 + 回填」——
  那样切完就发布的话，新快照不写 `assets`，**资产表会永远停在升级那天**。
  回填与双写必须同批发布。
- **验收口径收紧**：`assets` 按**身份键**（MAC 优先）聚合，而 `query_history()`
  按 **IP** 聚合 —— 换过 IP 的设备前者 1 行、后者 N 行。所以「逐台一致」
  **只在「有 MAC 且 IP 没变过」的设备上成立**；那个差异恰恰是本项要交付的改进，
  不是 bug。测试按这个口径写，**不假装两者永远相等**。
- **`seen_count` / `first_seen` / `last_seen` 是累积列，不是从观测重算**。
  `prune()` 会删旧快照（连带 `devices` 行），首见时间不能跟着被删掉 ——
  所以只在写入时按 `MIN` / `MAX` / 自增推进，永不回退。有测试盯着。

**回填失败的处理**：只在最后 `commit` 一次 → 失败则库原样留在「`assets` 空」的
状态，**下次启动自动重试**；且失败**不拦**程序打开库（资产表是增强，不是前提）。
重试条件是「`assets` 空 且 有能算出身份键的设备行」，所以全是空 MAC 空 IP 的库
不会每次启动空跑。

⚠ **一个还没解决的成本**：回填发生在**第一次连接**时，GUI 上就是**主线程**。
/24 的典型库是几千行、瞬时；但 /16 × 20 快照（百万行级）那次升级会**冻住界面**。
本轮没处理（一次性、有日志），③ 若要接进度条或挪到后台线程再动。

### 1.2 互操作导出包（资产表的第一个消费方）

| 项 | 值 |
|---|---|
| 优先级 | **P0** |
| 工时 | **3–5 天** |
| 依赖 | 1.1（NetBox CSV / Zabbix LLD 直接读 `assets`） |
| 原编号 | 建议书 v1.8 #7；`ROADMAP_V1.8.md` §3 |

**为什么是它**：资产表是一次**结构改动**，如果没有消费方，它就是一笔投机。
导出包是**最便宜的消费方**（纯读 + 纯写文件，零网络、零新依赖），
而它把「结构」变成「别人能用的东西」——这是「台账」这个定位唯一能拿到的**外部**认可。

⚠ **为什么不是 #6 只读 HTTP API（`ipscanner serve`）**：那会**开一个监听端口**。
本项目最强的差异点是「本地、无账号、不开服务」（建议书 §9 陷阱清单第 1 条：
云端 MSP / 强制账号是该品类第 7 大抱怨）。一旦 `serve` 存在，用户立刻会问
「要不要认证 / 防火墙怎么放 / 能不能只绑 127.0.0.1」—— 而答案全是**新的攻击面
与新的运维负担**。**文件型导出拿到同样的集成价值，不背这些。**

**现状（已实测）**：

- 四种格式的**数据都已齐**：
  - Nmap XML 需要 ip / hostname / mac / open_ports → `devices` 都有；
  - NetBox CSV 需要 hostname / ip / mac / vendor / device_class / location / …
    → `devices` 的列**覆盖了它的非外键字段**（不是巧合：Excel 匹配字段当初就照
    资产台账设计的）。⚠ 但 NetBox 的 `site` / `device_type` / `device_role` 是**外键**，
    导入前得先解析成名字 —— 这正是建议书把这条写作「NetBox **外键解析** CSV」的意思，
    也是本项里唯一需要动脑的地方；
  - Zabbix LLD 需要 ip / hostname + 发现项；
  - Oxidized `router.db` 只需 `name:model:group` → 拓扑节点已有 `model`
    （`topology_discovery.py:117`，由 `sys_descr` / `platform` 填充）。
- 导出框架**已有**：`excel_handler.py` 里 `export_csv()` / `export_json()` /
  `export_html()` / `export_results()`（XLSX）四个产出函数，GUI 侧由
  `export_mixin.py` 接线 —— 本项是**加格式**，不是建框架。
- ⚠ Nmap XML **读入**是另一件事：风险不在 XML 解析，而在**语义**
  （Nmap 的 host 状态机与我们的 `status` 不是一回事）。**产出先做，读入单列**
  （见 §3）。

**做法**：

- **产出四件**：`nmap.xml`（`<host>` + `<ports>`，含 `reason` / `method` 属性）、
  `zabbix_lld.json`、`netbox.csv`（列名照 NetBox 的 import 表头）、`router.db`。
- **统一入口**：GUI 导出对话框加格式下拉；CLI
  `ipscanner export --format nmap|zabbix|netbox|oxidized`。
- **语言无关**：导出的**值**必须是规范值（`status` 落 `online` / `offline`，
  `device_class` 落中文源串），**不能落 `tr()` 之后的展示串** ——
  这是 i18n 铁律（「存储/比较用规范值，只在展示时翻译」）在导出上的直接推论：
  导出文件会被**别的系统**解析。
- ⚠ **Nmap XML 的 `<os>` 段不编**：我们只有 `os_guess`，没有可靠 OS 指纹。
  编一个 `<osmatch>` 是**撒谎** —— 宁可少一段（延续「诚实降级」原则）。

**验收（可写成测试）**：

- 四种格式各有一份**逐字节快照测试**（golden file）—— 导出是给别人解析的，
  格式漂移是**静默**的，必须钉死；
- `netbox.csv` 的表头与 NetBox 的 CSV importer 官方表头一致（列名 + 必填项）；
- **语言切换（zh-CN / en-US）下导出的文件内容完全一致** ——
  这条测试同时是「没有落展示串」的证明；
- 0 台设备时产出**合法的空文档**，不是空文件、不是畸形 XML。

**落地记录位**：✅ 已落地（v1.9 §1.2 完成，commit 见下方）。

- 新增 `interop_export.py`：四格式的纯渲染函数（`render_nmap_xml` /
  `render_zabbix_lld` / `render_netbox_csv` / `render_router_db`）+ 分发器
  `build_interop()`（返回字节，便于 golden file）/ `export_interop()`。
  **零 PyQt / 零网络 / 零新依赖 / 语言无关**——导出值是规范值
  （`status`→online/offline、`device_class`→中文源串），绝不落 `tr()` 展示串。
- 四格式要点：
  - Nmap XML：含 `<host>/<address>/<hostnames>/<ports>/<status>`；⚠ **不编 `<os>`**
    （只有 os_guess，编 `<osmatch>` 是撒谎，延续诚实降级）。
  - Zabbix LLD JSON：`{"data":[{ "{#IP}","{#HOSTNAME}","{#MAC}","{#DEVICE.CLASS}",… }]}`。
  - NetBox 设备 CSV：表头与官方 importer 一致（必填 `name/device_type/device_role/
    site/status` 在最前）；`device_type`="Manufacturer Model"（vendor + device_class）、
    `status`→Active/Offline、`site`←location、`device_role`←device_class 按名字解析外键。
  - Oxidized `router.db`：`name:model:group`（model←device_class、group←location）。
- 消费方接线：CLI `ipscanner export --format nmap|zabbix|netbox|oxidized`
  （复用 1.1-③ 读路径 `list_assets`）；GUI `文件` 菜单「导出资产（互操作）...」
  → `export_mixin._export_assets_interop`（遵循 tr / ui_msg / audit_log.CAT_EXPORT）。
- 验收：`tests/test_interop_export.py` 四格式 **golden file 逐字节** + 0 台合法空文档
  （可解析 XML 根 / 带表头 CSV / `{"data":[]}` / 空 router.db）+ **语言无关**
  （zh-CN/en-US 字节完全一致）+ 外键解析，全绿；`ruff` 通过。
- ⚠ 约束：GUI 动作本机冒烟**未跑**（沙箱无 PyQt5）；当前导出**整张资产表**
  （资产视图筛选条是后续项，届时改为跟随其筛选，与 `_export_results` 同口径）。

### 1.3 拓扑可读性包（折行 + 文本导出）

| 项 | 值 |
|---|---|
| 优先级 | **P1** |
| 工时 | **3–4 天** |
| 依赖 | 无（**验收守卫已就位**） |
| 原编号 | 建议书 v1.8 #9；建议书 §4.4 |

**为什么是它**：这是全项目**唯一一个「数据齐了、算得也快、但显示不下」**的问题。
建议书 §5.2 实测：布局本身**不是**瓶颈（1000 节点 15 ms、5000 节点 259 ms），
**是排版策略** —— 10 交换机 → 画布 **7326×990**，50 交换机 → **36926×990**。

**现状（已实测）**：

- **验收标准已经写好、而且已经挂在那里催**：`AspectRatioAcceptanceTest`
  里达标档作回归守卫，未达标的宽高比条目标着 **`@expectedFailure`** ——
  本项落地后它们会**自动变成失败**，逼你摘掉标记。这是 `ROADMAP_V1.8.md` §6
  刻意留下的钩子（当时写的原话就是「v1.9 #9 落地后会自动报错催摘」）。
- 文本版拓扑导出**同类产品都不做**（建议书 §4.4 的原话），
  而实现成本几乎为零：拓扑已经是**树**，缩进就是文本。

**做法**：

- **折行**：tidy tree 算出坐标后，若**宽高比 > 3:1**，把并列子树**按行装箱**
  （第一层按固定列数换行）—— 等价于把「一排交换机」变成「一片」。
- **文本导出三种**：树形缩进 / Markdown 表格 / ASCII，含端口与协议；
  CLI `ipscanner topology --text`。
- ⚠ **端口利用率 / 空闲口视图移出本项**（见 §3）：它依赖 `--switch-map`
  采到的转发表，而那个开关**默认是关的** —— 一个默认没数据的视图会让人
  以为「我的交换机一个设备都没接」，比没有这个视图更糟。

**验收（可写成测试）**：

- 10 交换机与 50 交换机的布局**宽高比 ≤ 3:1**（`expectedFailure` 摘除后转正）；
- 折行后**节点不重叠**、连线不穿越节点（沿用现有布局测试的重叠断言）；
- 文本导出在三种格式下都包含**每一台交换机与它的每个下游节点** ——
  不许因为折行/分栏丢节点。

**落地记录位**（2026-10-12，v1.9 第 4 项 / 收官）：

- **折行**：`layout_real_topology` 在骨干 tidy tree 后新增「过宽折行」装箱
  通道（阈值 `_WRAP_MAX_ASPECT=3.0`；像素预算 `_WRAP_MAX_EDGE=4000` /
  `_WRAP_MIN_EDGE=600`，设备过多时退而只保宽高比）。仅当现状宽高比 > 3:1 才动手；
  并列子树整体平移、内部 tidy-tree 坐标不变，不丢节点、不新增重叠。
- **文本导出三种**：`topology_discovery.py` 新增 `TOPO_TEXT_FORMATS` 与
  `render_topology_tree` / `render_topology_markdown` / `render_topology_ascii`
  / 分发器 `render_topology_text` —— **纯函数、遍历整棵拓扑树（不依赖坐标）、
  含端口与协议、语言无关**（kind/state 用 up/down 规范值、device_class 用库规范串）。
  节点覆盖靠 `_topo_forest` 只收「BFS 实际用到的根」避免重复打印（已修过一次
  候选根被当成顶层再画一遍的 bug）。
- **CLI `ipscanner topology --text`**：新增 `topology` 子命令
  （`-r/--range` 必填、`--format tree|markdown|ascii`、`-o`、`--gateway`、
  `--no-snmp`、`--snmpv3-*`），复用 `_run_scan` + `discover_topology` +
  `render_topology_text`。
- **验收守卫去 `@expectedFailure`**：`AspectRatioAcceptanceTest` 从依赖 PyQt 的
  `test_topology_layout.py` **迁出**到新建的 **PyQt 无关** `tests/test_topology_layout_pure.py`，
  并转正为真正的回归守卫（宽高比 ≤3:1 + 像素预算 ≤4000/≥600）；
  新增 `TopologyTextExportTest`（三格式覆盖全部节点、含端口与协议、非法格式抛
  `ValueError`、空拓扑返回空串）。⚠ `test_topology_layout.py` 的 Qt 渲染测试
  仍在原文件、本机（有 PyQt5）环境照常跑。
- **验收（实测，9 个纯测试全绿、`ruff` 通过）**：
  - 10 交换机 / 100 终端宽高比 **2.02**、50 交换机 / 100 终端 **2.74**，均 ≤ 3:1；
  - 像素预算：(1,1000)=2750/2294、(4,100)=2266/1910、(10,100)=3866/1910 均落在
    [600, 4000]；
  - 文本导出三格式对 fixture（6/30、10/100、50/100）**逐节点覆盖**，无丢节点、
    含 `LLDP`/`FDB` 与端口 `GE0/1`/`GE1/0/1`。
- ⚠ 约束：本机 GUI 冒烟**未跑**（沙箱无 PyQt5）；`topology` 命令需真实扫描，
  本次只在解析层（-h）与纯函数层验证，未发起网络扫描。

### 1.4 质量门禁（资产表的安全网）

| 项 | 值 |
|---|---|
| 优先级 | **P1** |
| 工时 | **2–3 天** |
| 依赖 | 无 |
| 原编号 | 建议书 v1.8 #12（**后半**） |

**为什么是它**：v1.9 的主题项（1.1）是本项目**历史上最大的一次数据模型改动** ——
新增两张表、双写、回填老库、切换读路径。现在拦住它的只有 **1702 个测试方法**
（**72** 个测试文件），而**没有任何工具告诉你哪块代码根本没被覆盖到**。
**改动越大，测试的盲区越致命** —— 覆盖率在这里不是「工程洁癖」，是回滚的前提。

**现状（已实测）**：

- 覆盖率 / pyright / `pip-audit` **一处都没有**：
  `pyproject.toml`、`requirements.txt`、`requirements-dev.txt`、两个工作流文件里
  **0 处**引用。
- 质量工程的其他缺口（i18n 死键、色值禁令、BER fuzz、宽高比验收）
  v1.8 已**全部**补上（见 `ROADMAP_V1.8.md` §6），**只剩这三项**。
- `ci.yml` 已是 **3 个 job**（Windows × 4 个 Python 版本 / 跨平台 OS / PyInstaller 打包验证），
  加门禁有现成的位置。⚠ **它没有语言矩阵** —— 但 CI runner 是**英文系统**，
  所以 CI 上跑的是 en-US 那一侧、本机跑的是 zh-CN，两边合起来才覆盖到语言相关代码
  （这也是「测试绝不写死界面文案」那条铁律的由来）。
- **两条基线已实测（2026-10-11，用于定门槛，别再估）**：
  - 产品代码覆盖率 **71%**（14 735 statements / 缺 4 333）。⚠ **口径**：必须
    `--omit="tests/*"` —— 含测试的 TOTAL 是 **83%**，那是虚高（测试文件本身 99%，
    把分母拉大了）。最低几档：`main.py` / `oui_updater.py` / `parse_ieee_oui.py`
    **0%**、`ui_dialogs/reports.py` **12%**、`excel_handler.py` **21%**。
  - ⭐ **而 1.1 要动的两个文件反而是最高的**：`history_store.py` **94%**
    （362 / 缺 20）、`db_util.py` **90%**（83 / 缺 8）。
  - pyright 跑 `scanner/` + 8 个零 Qt 模块：**70 errors**。但
    **`db_util.py` 0 条、`history_store.py` 2 条** —— **68 条都不在 1.1 要动的文件里**。
    其中 **22 条 `reportPossiblyUnboundVariable` 全在 `scanner/cred_store.py:30–60`
    一个簇**，是**结构性假阳性**：`try: import ctypes … _HAS_DPAPI=True
    / except AttributeError: _HAS_DPAPI=False`，然后 `if _HAS_DPAPI:` 里才用
    `ctypes` —— **pyright 无法跨布尔标志窄化**，于是判这些名字"可能未绑定"。
- ⚠ `.gitignore` **不忽略** `.coverage` —— 加覆盖率时要顺手补这一行，
  否则测量产物会被提交进去。

**做法**：

- ⚠ **覆盖率：设 per-file 下界，不设全局棘轮**。
  **`history_store.py` ≥ 94%、`db_util.py` ≥ 90%**（按上面的实测值定），
  全局数字**只出报告、不进门槛**。
  - 理由：全局 71% 会被与 1.1 无关的 0% 文件稀释 —— 1.1 新增代码时中间提交必然掉
    全局百分比 → **假红** → 人就去调低门槛。这恰恰是本节自己引用过的教训
    （「假红会让人习惯性地忽略红」）。
  - per-file 才防得住**真正要防的事**：1.1 在 `history_store.py` / `db_util.py`
    里新增的代码必须被测到。而这两个文件现状就是 94% / 90%，下界**可达**。
  - 「改动前基线」的价值靠**记录数值**实现，不需要靠棘轮去实现。
- ⚠ **pyright：门禁只钉「1.1 要动的文件」，不是「整个领域层 0 error」**。
  - 实测 `db_util.py` **0 条**、`history_store.py` **2 条** —— 开工即可做到 0 error。
  - 那 2 条是**真问题**，顺手修掉：`history_store.py:220` 声明 `-> int` 却可能返回
    `None`；`:244` `get_snapshot()` 注解 `-> dict`、而它自己的 docstring 写着
    「不存在返回 None」—— **注解与文档不一致**，会误导 1.1 的作者。
  - 其余 68 条进**基线文件**（注明理由）或按规则豁免 —— 例如
    `reportPossiblyUnboundVariable` 在 `cred_store.py` 那个"布尔标志守卫条件导入"
    的模式下是**假阳性**。
  - ⚠ 若按原写法要求"领域层 0 error"，本项会从 2–3 天变成一次全领域层整改，
    而且大部分工作量**不在 1.1 要碰的文件里** —— 那是给 1.1 拖时间，不是给它兜底。
  - **UI 层不开**：Qt 的类型存根质量会制造大量噪声；而「领域层零 Qt」
    恰好让这一层是干净的（这也是本项目架构上最值得守的一条）。
- **`pip-audit`**：本项依赖极少（PyQt5 三件套 + openpyxl + xlrd），跑得飞快；
  它**同时是「零依赖身份」的守卫** —— 哪天有人顺手加了个包，门禁会问一句。

⚠ **不许把门禁写成「允许失败」**：三个工具都进 CI 的**必过**任务。
一个「允许红」的门禁等于没有门禁 —— `ROADMAP_V1.8.md` §6 已经吃过这个教训的
变体：`NoColorLiteralTest` 的口径从「源码正则」改成「AST 只看代码」，
就是因为原口径会产生**假的红**，而假红会让人**习惯性地忽略红**。

**验收（可写成测试）**：

- 三个工具在 CI 里各占一个任务，**红了就拦合并**；
- 覆盖率下界写进**配置**（不是写进文档），且是 **per-file**（`history_store.py`
  / `db_util.py`），不是全局百分比；
- pyright 在 **1.1 要动的文件**上 **0 error**（存量 68 条走基线文件 + 按规则豁免，
  每条都要写明理由；**不许 `# type: ignore` 一把梭**）；
- **基线数值记进本文档的落地记录** —— 这是「改动前基线」唯一的存档处，
  也是判断 1.1 有没有把这两个文件的覆盖率做低了的依据。

**落地记录（2026-10-11，已完成）**：

- **实测基线（本节所有门槛都是照这两个数定的，不是拍的）**：
  - 产品代码覆盖率 **71%**（14 738 statements / 缺 4 334）。⚠ 含测试文件的
    TOTAL 是 **83%**，那是虚高 —— 必须 `--omit="tests/*"` 才是真实口径。
  - `history_store.py` **95%**（365 / 缺 20）、`db_util.py` **90%**（83 / 缺 8）——
    **1.1 要动的两个文件反而是全项目最高的两档**，所以下界可达。
- **三个门禁各占一个 CI job**（`quality-coverage` / `quality-types` /
  `quality-audit`）：红了拦合并，且一眼看得出是**哪一个**红的。
- **覆盖率**用 `coverage` 而不是 `pytest-cov` —— 本项目跑的是标准库 `unittest`
  （`run_tests.py`），压根不过 pytest。逐文件各跑一次
  `coverage report --include=<文件> --fail-under=<n>`。
  - ⚠ **匹配不到文件时 coverage 以退出码 `1` 失败**，不是静默通过 ——
    所以改文件名 / 打错字会当场红。实测三种退出码：无数据 `1`、未达标 `2`、达标 `0`。
  - 下界的规则是「**不许变低**」；要放宽必须在提交信息里写明理由，
    否则"下界"会变成"每次掉下去就调一下"的橡皮筋。
- **pyright** 锁 `1.1.414`（新版会新增规则，让干净的文件莫名变红）。
  检查范围是**包含清单**（`pyproject.toml` 的 `[tool.pyright].include`），
  不是排除清单 —— 好处是**不需要维护一份会随 pyright 版本漂移的「已知错误基线」**。
  - 顺手修掉那 2 条真问题：`history_store.py:220` `save_snapshot()` 声明 `-> int`
    却可能返回 `None`；`:244` `get_snapshot()` 注解 `-> dict`、
    而它自己的 docstring 写着「不存在返回 None」—— **注解与文档不一致**，
    1.1 的作者会被它误导。
  - ⚠ `:220` 那条**不是**为了过类型检查才加的：它挡的是**静默坏数据** ——
    rowid 拿不到还继续写，设备就会挂在 `snapshot_id=None` 下，**写得进去却永远
    查不到**，比当场报错难查得多。所以不返回 0 之类的假 id。守卫自己也有测试
    （`SnapshotRowidGuardTest` 3 项）。
- **`pip-audit`** 只审 `requirements.txt`（开发依赖不进发布产物）：**零告警**
  （完整解析版同样零告警，且会多审一个传递依赖 `et_xmlfile`）。
  - ⚠ **它不在 `ci.yml` 里，单独一个 `dependency-audit.yml`**，触发条件是
    **每周一 + `requirements.txt` 变更时 + 手动**。改过两版才定下来，两版都是被
    CI 打回来的：
    1. 第一版挂在每次 push 上 → **红了**。查下来不是真有漏洞（本机跑零告警）。
    2. 第二版加 `--no-deps` + `--timeout 60` → **还是红了**。
       两次都确认过「真有漏洞 / 解析失败」这个二分：本机 `--no-deps` 退出码 0，
       完整解析版也是 0。
  - **根因判断**：它是 **唯一要联网**的门禁，而它审的东西**不会随提交变化** ——
    依赖有没有 CVE，只在「改了 requirements.txt」或「CVE 库新收录一条」时才变。
    把它挂在每次 push 上，等于让**网络状况**来决定 CI 红不红。
  - 于是移出关键路径：频率降到「每周 + 改依赖时」，偶发的网络失败只是
    **一次需要重跑的黄**，而不是拦住别人的红。这也更贴合风险本身 ——
    CVE 是随时间出现的，不是随提交出现的。
  - `--no-deps` 那一层**保留**（不做依赖解析，只审精确锁定的那几个包），
    代价是不覆盖传递依赖 —— 由同文件里第二步「完整解析版、
    `continue-on-error`」补上报告。**门禁与报告分开**：真有漏洞时第一步就红了，
    完整版只用来把 `et_xmlfile` 这类传递依赖覆盖上。
- 三个工具的版本写进 `requirements-dev.txt` 并锁死；`.gitignore` 补 `.coverage`
  （原先**不**忽略，测量产物会被提交进去）。

**反向验证（6 处注入，6/6 命中）**：下界抬高 1 点 → 红；`--include` 打错字 → 红；
注入一条 pyright 类型错误 → 红；塞一个已知有漏洞的旧依赖 → 红；
外加两条「必须绿」的对照（下界等于实测值、真实 `requirements.txt`），
用来证明前面那些红不是因为环境坏了。

> **写这条守卫时踩到的一个坑**（值得记）：给「拿不到 rowid 就报错」写测试时，
> 第一版 helper 在 `mock.patch` **之后**才去调 `history_store._conn()`，
> 拿到的已经是 patch 后的自己 → 无限递归 → 抛 `RecursionError`。
> 而 **`RecursionError` 是 `RuntimeError` 的子类**，`assertRaises(RuntimeError)`
> 会**误判通过**。是那条「反向确认注入真的生效了」的断言把它抓出来的 ——
> 改法：原函数必须在 patch **之前**取，并且用 `assertRaisesRegex` 钉住 message。
