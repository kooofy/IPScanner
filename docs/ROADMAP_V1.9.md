## 0. 重排原则

1. **一个 minor 只承载 4 项** —— 让「v1.9 交付了什么」能被一句话说清。
2. **四项各占一个不可替代的角色**：
   - ① **结构**（动数据模型）—— **资产表 + 观测表**；
   - ② **出口**（让结构产生对外价值）—— **互操作导出包**；
   - ③ **显示**（数据齐了但画不下）—— **拓扑可读性包**；
   - ④ **安全网**（让这次大改可回滚）—— **质量门禁**。
3. **优先级不由「重要」决定，由「是否阻塞其它项」决定** —— 资产表本身用户看不见，
   但**报表、导出、趋势类功能全都要先读它**，所以它是 P0 主题项。
4. **保持项目身份** ——
   - 不引入第三方依赖 → 通知渠道 **#8 Apprise 继续出局**；
   - **不开网络监听端口** → 只读 HTTP API（#6）让位给**文件型导出**（1.2）。
5. **每一项都要能独立回滚** —— 1.1 是本项目**历史上最大的一次数据模型改动**，
   双写 + 老库备份是硬要求（建议书 §5.1 的原话），不是可选项。

## 1. v1.9 四项

### 1.1 资产表 + 观测表（v1.9 主题项）

| 项 | 值 |
|---|---|
| 优先级 | **P0**（v1.9 主题项） |
| 工时 | **8–12 天** |
| 依赖 | `user_version` 迁移链 ✅ **已就绪**（1.8.0 之后已落地） |
| 原编号 | 建议书 v1.9 #1；详见建议书 §4.3 / §5.1 |

**为什么是它**：现在「台账」不是一个**东西**，而是「最后一份快照」的别名。三处硬证据：

- `devices` 表**没有** `first_seen` / `last_seen` 列 —— 首见/末见时间是
  `query_history()` 靠**按快照时间升序遍历 + 内存聚合**推导出来的
  （`history_store.py:837` 的说明就是这么写的）；
- `port_map` 与 `security_findings` 都**以 `snapshot_id` 为维度**，
  所以「这个端口接了几台设备」「Telnet 开了多久」都要**把 N 份快照读一遍**才算得出来；
- 后果：趋势类问题（在线率曲线、首次出现告警、**端口长期暴露时长**、MTBF/抖动）
  现在要么做不到，要么贵到不敢放进交互路径。

**现状（已实测，2026-10-11 复核）**：

- 五张表 `snapshots` / `devices` / `switch_map` / `port_map` / `security_findings`，
  **全部以快照为维度**。`devices` 的一行 = 「**某快照里的**某台设备」，
  不是「一台设备」—— 同一台机器扫 3 次就有 3 行。
- `devices` 已有 `location` / `user` / `remark` 三列（Excel 匹配字段）——
  资产表要的「人工维护字段」**雏形已经在**，不用新造概念。
  ⚠ 但它们在 `devices` 上意味着**每次快照都重存一遍**：改一次备注要改 N 行。
- ⚠ **`devices` 不存服务**：`scanner/models.py:23` 的 `services` 与 `:35` 的
  `service_details` 在内存里是齐的，但 `history_store.py` **一次都没写过它们**
  （全文件 **0 处**引用）—— 服务是「采集到、在数据库门口丢掉」。
  **推论（对工时是好消息）**：资产表要补服务清单，**不需要新增任何探测**，
  只需补一次写入。
- 迁移链已就绪：`user_version` + `MIGRATIONS` 已在 1.8.0 之后落地
  （`db_util.apply_migrations()`，`SCHEMA_VERSION = 3`，含**老库版本推断**）。
  **资产表就是第 4 版迁移** —— 这也是「为什么现在能做、以前不能」的直接答案。

**做法**：

- **新增两张表**：
  - `assets`（一行 = **一台设备**）：`identity_key`（MAC 归一化后大写）、
    `first_seen` / `last_seen` / `seen_count`、当前 ip/hostname/vendor/device_class/
    os_guess、`location` / `user` / `remark`、`custom_json`；
  - `asset_observations`（一行 = 一台设备在**某快照**的一次观测）：
    保留 `snapshot_id` 外键 + `CASCADE`，装 `ip` / `status` / `open_ports` /
    服务清单 / `risk_score`。
  - `snapshots` 表**语义不动** —— 快照是用户能理解的心智模型
    （「10 月 9 日那份清单」），资产表是**实现**（建议书 §5.1 第 3 条）。
- **迁移 v4**：**不用 `IF NOT EXISTS`**。迁移链的规矩是「第 4 版起结构不符要报错，
  不要静默跳过」（见 `history_store.py` 头部注释）。
- **双写**（建议书 §5.1 的硬要求）：`save_snapshot()` 照旧写 `devices`，
  **同时**写 `assets` / `asset_observations`；读路径**逐步**切换，
  `query_history()` 全程保持可用。
- **老库自动升级 + 保留备份文件**：升级前把库文件复制一份（带版本号后缀），
  失败可整体回退。
- **回填**：升级老库时把已有快照**一次性**折进 `assets`，
  否则老用户升级后资产表是空的、等于没升。
- **`identity_key` 只认 MAC**：随机化 MAC 的**降级身份**接进主键是另一件事
  （见 §3），本项不动 `#11` 已有的指纹机制。

**验收（可写成测试）**：

- 升级一个**已有 3 份快照的老库** → `assets` 行数 = 去重后的 MAC 数；
  且 `first_seen` / `last_seen` 与 `query_history()` 的结果**逐台一致**
  （这是回填正确性的**唯一**硬标准）；
- 同一台设备连扫 3 次 → `assets.seen_count == 3`，`asset_observations` 3 行；
- **双写一致性**：一次 `save_snapshot()` 后，`devices` 与 `asset_observations`
  对同一 `(snapshot_id, ip)` 的 `status` / `open_ports` 一致；
- **可回滚**：升级前的库文件被备份，且备份文件能被**旧版本程序**打开
  （`user_version` 仍是旧值、表结构未被改写）；
- **读路径切换不改变对外行为**：老库升级后 `locate_device()` /
  `device_timeline()` / `query_history()` 结果与升级前**逐字段相同**。

**落地记录位**：待填（本项未开工）。

### 1.2 互操作导出包（资产表的第一个消费方）

| 项 | 值 |
|---|---|
| 优先级 | **P0** |
| 工时 | **3–5 天** |
| 依赖 | 1.1（NetBox CSV / Zabbix LLD 直接读 `assets`） |
| 原编号 | 建议书 v1.8 #7；`ROADMAP_V1.8.md` §3 |

**为什么是它**：资产表是一次**结构改动**，如果没有消费方，它就是一笔投机。
导出包是**最便宜的消费方**（纯读 + 纯写文件，零网络、零新依赖），
而它把「结构」变成「别人能用的东西」——这是「台账」这个定位唯一能拿到的**外部**认可。

⚠ **为什么不是 #6 只读 HTTP API（`ipscanner serve`）**：那会**开一个监听端口**。
本项目最强的差异点是「本地、无账号、不开服务」（建议书 §9 陷阱清单第 1 条：
云端 MSP / 强制账号是该品类第 7 大抱怨）。一旦 `serve` 存在，用户立刻会问
「要不要认证 / 防火墙怎么放 / 能不能只绑 127.0.0.1」—— 而答案全是**新的攻击面
与新的运维负担**。**文件型导出拿到同样的集成价值，不背这些。**

**现状（已实测）**：

- 四种格式的**数据都已齐**：
  - Nmap XML 需要 ip / hostname / mac / open_ports → `devices` 都有；
  - NetBox CSV 需要 hostname / ip / mac / vendor / device_class / location / …
    → `devices` 的列**覆盖了它的非外键字段**（不是巧合：Excel 匹配字段当初就照
    资产台账设计的）。⚠ 但 NetBox 的 `site` / `device_type` / `device_role` 是**外键**，
    导入前得先解析成名字 —— 这正是建议书把这条写作「NetBox **外键解析** CSV」的意思，
    也是本项里唯一需要动脑的地方；
  - Zabbix LLD 需要 ip / hostname + 发现项；
  - Oxidized `router.db` 只需 `name:model:group` → 拓扑节点已有 `model`
    （`topology_discovery.py:117`，由 `sys_descr` / `platform` 填充）。
- 导出框架**已有**：`excel_handler.py` 里 `export_csv()` / `export_json()` /
  `export_html()` / `export_results()`（XLSX）四个产出函数，GUI 侧由
  `export_mixin.py` 接线 —— 本项是**加格式**，不是建框架。
- ⚠ Nmap XML **读入**是另一件事：风险不在 XML 解析，而在**语义**
  （Nmap 的 host 状态机与我们的 `status` 不是一回事）。**产出先做，读入单列**
  （见 §3）。

**做法**：

- **产出四件**：`nmap.xml`（`<host>` + `<ports>`，含 `reason` / `method` 属性）、
  `zabbix_lld.json`、`netbox.csv`（列名照 NetBox 的 import 表头）、`router.db`。
- **统一入口**：GUI 导出对话框加格式下拉；CLI
  `ipscanner export --format nmap|zabbix|netbox|oxidized`。
- **语言无关**：导出的**值**必须是规范值（`status` 落 `online` / `offline`，
  `device_class` 落中文源串），**不能落 `tr()` 之后的展示串** ——
  这是 i18n 铁律（「存储/比较用规范值，只在展示时翻译」）在导出上的直接推论：
  导出文件会被**别的系统**解析。
- ⚠ **Nmap XML 的 `<os>` 段不编**：我们只有 `os_guess`，没有可靠 OS 指纹。
  编一个 `<osmatch>` 是**撒谎** —— 宁可少一段（延续「诚实降级」原则）。

**验收（可写成测试）**：

- 四种格式各有一份**逐字节快照测试**（golden file）—— 导出是给别人解析的，
  格式漂移是**静默**的，必须钉死；
- `netbox.csv` 的表头与 NetBox 的 CSV importer 官方表头一致（列名 + 必填项）；
- **语言切换（zh-CN / en-US）下导出的文件内容完全一致** ——
  这条测试同时是「没有落展示串」的证明；
- 0 台设备时产出**合法的空文档**，不是空文件、不是畸形 XML。

**落地记录位**：待填（本项未开工）。

### 1.3 拓扑可读性包（折行 + 文本导出）

| 项 | 值 |
|---|---|
| 优先级 | **P1** |
| 工时 | **3–4 天** |
| 依赖 | 无（**验收守卫已就位**） |
| 原编号 | 建议书 v1.8 #9；建议书 §4.4 |

**为什么是它**：这是全项目**唯一一个「数据齐了、算得也快、但显示不下」**的问题。
建议书 §5.2 实测：布局本身**不是**瓶颈（1000 节点 15 ms、5000 节点 259 ms），
**是排版策略** —— 10 交换机 → 画布 **7326×990**，50 交换机 → **36926×990**。

**现状（已实测）**：

- **验收标准已经写好、而且已经挂在那里催**：`AspectRatioAcceptanceTest`
  里达标档作回归守卫，未达标的宽高比条目标着 **`@expectedFailure`** ——
  本项落地后它们会**自动变成失败**，逼你摘掉标记。这是 `ROADMAP_V1.8.md` §6
  刻意留下的钩子（当时写的原话就是「v1.9 #9 落地后会自动报错催摘」）。
- 文本版拓扑导出**同类产品都不做**（建议书 §4.4 的原话），
  而实现成本几乎为零：拓扑已经是**树**，缩进就是文本。

**做法**：

- **折行**：tidy tree 算出坐标后，若**宽高比 > 3:1**，把并列子树**按行装箱**
  （第一层按固定列数换行）—— 等价于把「一排交换机」变成「一片」。
- **文本导出三种**：树形缩进 / Markdown 表格 / ASCII，含端口与协议；
  CLI `ipscanner topology --text`。
- ⚠ **端口利用率 / 空闲口视图移出本项**（见 §3）：它依赖 `--switch-map`
  采到的转发表，而那个开关**默认是关的** —— 一个默认没数据的视图会让人
  以为「我的交换机一个设备都没接」，比没有这个视图更糟。

**验收（可写成测试）**：

- 10 交换机与 50 交换机的布局**宽高比 ≤ 3:1**（`expectedFailure` 摘除后转正）；
- 折行后**节点不重叠**、连线不穿越节点（沿用现有布局测试的重叠断言）；
- 文本导出在三种格式下都包含**每一台交换机与它的每个下游节点** ——
  不许因为折行/分栏丢节点。

**落地记录位**：待填（本项未开工）。

### 1.4 质量门禁（资产表的安全网）

| 项 | 值 |
|---|---|
| 优先级 | **P1** |
| 工时 | **2–3 天** |
| 依赖 | 无 |
| 原编号 | 建议书 v1.8 #12（**后半**） |

**为什么是它**：v1.9 的主题项（1.1）是本项目**历史上最大的一次数据模型改动** ——
新增两张表、双写、回填老库、切换读路径。现在拦住它的只有 **1702 个测试方法**
（**72** 个测试文件），而**没有任何工具告诉你哪块代码根本没被覆盖到**。
**改动越大，测试的盲区越致命** —— 覆盖率在这里不是「工程洁癖」，是回滚的前提。

**现状（已实测）**：

- 覆盖率 / pyright / `pip-audit` **一处都没有**：
  `pyproject.toml`、`requirements.txt`、`requirements-dev.txt`、两个工作流文件里
  **0 处**引用。
- 质量工程的其他缺口（i18n 死键、色值禁令、BER fuzz、宽高比验收）
  v1.8 已**全部**补上（见 `ROADMAP_V1.8.md` §6），**只剩这三项**。
- `ci.yml` 已是 **3 个 job**（Windows × 4 个 Python 版本 / 跨平台 OS / PyInstaller 打包验证），
  加门禁有现成的位置。⚠ **它没有语言矩阵** —— 但 CI runner 是**英文系统**，
  所以 CI 上跑的是 en-US 那一侧、本机跑的是 zh-CN，两边合起来才覆盖到语言相关代码
  （这也是「测试绝不写死界面文案」那条铁律的由来）。

**做法**：

- **覆盖率**：`pytest-cov` 出报告，**先只设下界 + 棘轮**（不许比上次更低），
  不追求百分比好看。重点看 `history_store.py` / `db_util.py` ——
  正是资产表要动的两个文件。
- **pyright 只开领域层**：`scanner/` + `db_util.py` + `history_store.py`。
  **UI 层不开** —— Qt 的类型存根质量会制造大量噪声，而「领域层零 Qt」
  恰好让这一层是干净的（这也是本项目架构上最值得守的一条）。
- **`pip-audit`**：本项依赖极少（PyQt5 三件套 + openpyxl + xlrd），跑得飞快；
  它**同时是「零依赖身份」的守卫** —— 哪天有人顺手加了个包，门禁会问一句。

⚠ **不许把门禁写成「允许失败」**：三个工具都进 CI 的**必过**任务。
一个「允许红」的门禁等于没有门禁 —— `ROADMAP_V1.8.md` §6 已经吃过这个教训的
变体：`NoColorLiteralTest` 的口径从「源码正则」改成「AST 只看代码」，
就是因为原口径会产生**假的红**，而假红会让人**习惯性地忽略红**。

**验收（可写成测试）**：

- 三个工具在 CI 里各占一个任务，**红了就拦合并**；
- 覆盖率下界写进**配置**（不是写进文档），下次改动低于下界即失败；
- pyright 在领域层 **0 error**（如有存量 error，逐个修掉，或写进基线文件
  并注明理由；**不许 `# type: ignore` 一把梭**）。

**落地记录位**：待填（本项未开工）。

## 3. 被移出 v1.9 的 11 项及去向

> **不是丢弃，是排期。** 每项都写明「为什么不在 v1.9」。

| 原编号 | 事项 | 去向 | 理由 |

## 5. 建议的落地顺序

```
1.4（质量门禁，先立安全网） → 1.1（资产表 + 观测表，主题项）
      → 1.2（互操作导出包，消费方） → 1.3（拓扑可读性包）
```

- **1.4 排在最前**：它是 1.1 的**安全网**。等 1.1 做完再补门禁就晚了 ——
  那时已经没有「改动前」的覆盖率基线可比对，门禁只能从**已经包含新代码**的
  现状起算，等于放过这次大改。
- **1.1 之后立刻做 1.2**：资产表需要一个消费方来证明它值这笔钱；
  导出包是最便宜的那个，而且它逼着 1.1 的**字段设计**面向真实消费方
  （NetBox 的表头会告诉你 `assets` 缺哪一列）。
- **1.3 独立**，不碰数据层，可在 1.1 卡住时并行 ——
  但**不建议插到 1.1 中间**：双写与回填需要连续的心智上下文。
- 全程**不冻结补丁轨道**（见 §6）—— 该修的照修。
