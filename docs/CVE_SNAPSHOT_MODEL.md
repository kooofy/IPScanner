## 1. 设计三原则（从项目既有铁律直接推出）

1. **数据不出网**（`PRODUCT_ADVISORY.md` §9「内网工具的数据不能出网」）：
   运行期的 `cve_snapshot.py` **零网络** —— 不 import `urllib` / `requests` / `socket`，
   不发任何请求。更新快照 = 用户**手动**把新文件放进 `data_dir()`（同 `oui.db` 的更新方式）。
2. **声明式扩展，不执行代码**（§9「建议改成『声明式扩展』」）：
   快照是**纯数据**（JSON），**绝不含**正则以外的可执行逻辑，也不允许内联脚本。
   解析器只做数据 → 结构的映射，不做 `eval` / 不动态 import。
3. **诚实降级**（v2.1 §2.3 硬约束 + §9「绝不能给出暗示『已实测可利用』的结论」）：
   快照**缺失 / 过期 / 损坏** → 输出「**无 CVE 数据可查**」，
   与「查了、没有匹配」在返回值与文案上**可区分**。
   **宁可报「数据过期」，也不拿旧快照给用户一个过期的安心感。**

## 2. 谁生成：上游聚合方生成，本项目只消费

**裁定**：本项目**不生成快照**。快照由**上游权威源聚合**而成，本项目只做**消费端**。

### 2.1 上游权威源（全部公开、免费、有稳定 API/文件）

| 源 | 提供什么 | 形态 | 许可/成本 |
|---|---|---|---|
| **NVD**（NIST National Vulnerability Database） | CVE 条目 + CPE 匹配串（`cpeMatch`） | JSON feed（按年 / 按最近修改） | 公有领域（US Gov） |
| **CISA KEV** | 「已被实际利用」的 CVE 清单 | 单个 JSON（`known_exploited_vulnerabilities.json`） | 公有领域 |
| **FIRST EPSS** | 每个 CVE 的利用概率分值（0–1）+ 百分位 | 每日 CSV（gzip） | 免费（FIRST 许可） |

> ⚠ **本项目不直接消费这三者的原生大文件**（NVD 全量数百 MB、CPE 字典巨大），
> 而是消费**上游聚合后的精简快照**（见 §2.2）。谁聚合？—— 两条路，**产品侧只承诺第 1 条**：

### 2.2 两条生成路径（产品只承诺路径 A）

**路径 A（推荐、产品承诺）：社区/维护者发布的「精简快照」**
- 一个**版本化的 release 数据文件**（例如挂在某个公开仓库的 release 或本仓库的
  `data/` 可下载附件），字段只含本工具需要的：`cve_id` / 受影响的**粗粒度** CPE /
  `kev` 布尔 / `epss` 分值 / `generated_at`；
- 用户下载这个**单文件**，放进 `data_dir()`，完事；
- 本项目的**运行期代码只认这个通用格式**（见 §4），不关心它是谁生成、怎么生成。

**路径 B（可选、不承诺）：用户/贡献者本地自行聚合**
- 提供 `tools/build_cve_snapshot.py`（**仅供离线手工运行，不进任何打包产物、
  不被运行期 import**）：读 §2.1 三个源的本地副本 → 产出 §4 格式；
- 这条**不是产品功能**，是「想自己做的用户的自助工具」；CI 不跑、发行包不含。

> **为什么不让运行期直接拉 NVD**：违反原则 1（数据不出网）。**为什么不让内置自动更新**：
> 违反原则 2 之外的运维现实 —— 一个单人维护项目承诺「每日自动更新一个数百 MB 的外部
> 数据库」是给自己挖坑，而且内网机器本来就连不上。**手动、单文件、可审计**才是对的。

## 3. 多久更新 + 放哪 + 怎么验签（三个工程问题的答复）

### 3.1 多久更新：快照自带新鲜度，过期显式降级

**不打「自动每日更新」的包票**，改用**数据自带的新鲜度声明**：

- 快照文件含 `generated_at`（ISO 8601 UTC）与 `max_age_days`（整数，生成方声明）；
- 运行期加载后计算 `age = now - generated_at`：
  - `age ≤ max_age_days` → 正常使用，报告里标注**快照日期**；
  - `age > max_age_days` → **降级**：仍可用（用户自己选的），但输出**显式标注
    「快照已过期 N 天，结论可能滞后」**；**绝不**静默当新鲜数据用；
- **建议默认 `max_age_days = 30`**（CVE/EPSS 变动以周/月计，30 天足够警示；生成方可覆写）；
- `generated_at` **缺失** → 视为**未知新鲜度**，与「过期」同级告警（不假设它新鲜）。

> **约定**：本项目**不**提供「点一下自动更新」（那必然联网）。更新动作在文档里写清：
> 「下载新快照 → 覆盖 `data_dir()/cve_snapshot.json`」。

### 3.2 放哪：沿用 `data_dir()` → `resource_dir()` 回退（项目既有约定）

**直接复用** `oui.db` / `service_fingerprints.json` / `report_engine` 模板的**同一套策略**
（源码原话：「**优先 `data_dir()`（用户可更新）→ 回退 `resource_dir()`（内置）**」）：

```
查找顺序：
1) data_dir()/cve_snapshot.json        ← 用户下载/更新的版本（优先）
2) resource_dir()/cve_snapshot.json    ← 发行包内置的种子（可能为空/极简）
```

- **两个目录的分工**（照 `app_paths.py` 定义）：
  - `resource_dir()` = 打进 exe 的只读资源 → 放**内置种子**（可为空文档或极小的常见集）；
  - `data_dir()` = 用户持久化目录 → 放**用户更新版**；
- **打包要求**（照长期记忆的硬约定）：新增运行时资源（若内置种子非空）必须
  同时进 **GUI spec 的 `datas`** **且** CI 断言到**具体文件**；
- **可移植版**（`is_portable()`）下 `data_dir()` 落在 exe 同级 → 天然支持「U 盘带着快照走」。

### 3.3 加载稳健性：坏了只降级，不升级成扫描失败

照 `service_fingerprints.py` 的稳健性口径（源码原话：「数据文件缺失 / 损坏 / 正则写错，
都**不能**让『指纹库坏了』升级成『扫描失败』」）：

- 文件不存在 → `warning`「无 CVE 快照，本次不产出暴露面」+ 返回**空结构**（非异常）；
- JSON 解析失败 / 结构不符 → `warning` + 返回空结构 + **绝不抛**；
- 单条 CVE 记录字段缺失/类型错 → **跳过该条并留痕**，其余照常；
- 全程 `get_logger(__name__)`，**禁止** `print` / `stderr.write`（项目日志策略棘轮）。

### 3.4 怎么验签：SHA256 摘要清单（与发布流程同口径）

**裁定：用 SHA256 摘要清单，不做 PGP/代码签名。** 理由：

1. **威胁模型匹配**：快照是**只读数据**（原则 2），不是可执行代码 —— 最现实的风险是
   **下载损坏 / 半截文件 / 被中间篡改**，而非「恶意代码执行」。摘要清单覆盖前者。
2. **零依赖**：`hashlib.sha256` 是标准库，**不引入 GnuPG**（破原则「不加依赖」）；
   签名验证库（`pgpy` 等）在本项目是过度工程。
3. **与既有流程一致**：本项目的 Release 产物就是 `SHA256SUMS.txt`（LF、无 BOM），
   用户已习惯这个口径 —— 快照沿用同一格式，**心智负担为零**。
4. **可选强化**（不阻塞）：快照**和**它的 `.sha256` 由同一个可信来源分发时，
   摘要能防「传输损坏/半截」；**若将来需要防「来源被冒充」**，再单列提案加签名，
   **不放进 2.3 的范围**（避免范围蔓延）。

**验签流程**（运行期，纯标准库）：

```
cve_snapshot.json   +   cve_snapshot.sha256（格式同 SHA256SUMS.txt：<hex>␣␣<文件名>）
  → 加载前先算 sha256 → 与清单比对：
     一致   → 正常加载；
     不一致 → 拒绝加载 + warning「快照摘要不匹配，可能损坏」→ 降级为「无数据」；
     清单缺失 → **不阻断**（摘要可选）：warning「未找到摘要清单，按原样加载（未校验）」
                —— 但 freshness 照常判定（§3.1）。
```

> **为什么摘要清单「缺失不阻断」**：强制要求 `.sha256` 会把「只想快速试一下」的用户
> 挡在门外，和「可选增强层不挡主流程」的项目哲学冲突。有则校验、无则告警，是平衡点。

## 4. 快照格式（草案 v1）

**纯 JSON、单文件、语言无关**。字段名用**英文固定键**（照 CLI JSON 键固定英文的约定）。

```jsonc
{
  "schema": "ipscanner.cve_snapshot/1",   // 格式版本，便于将来演进
  "generated_at": "2026-10-01T00:00:00Z", // ISO 8601 UTC，生成时间
  "max_age_days": 30,                     // 生成方声明的新鲜度上限
  "sources": {                            // 溯源（可审计，不参与匹配）
    "nvd": "2026-10-01",
    "kev": "2026-09-30",
    "epss": "2026-10-01"
  },
  "cves": [
    {
      "cve_id": "CVE-2021-44228",
      "cpe": [                            // 粗粒度 CPE（产品级，见下注）
        "cpe:2.3:a:apache:log4j:*:*:*:*:*:*:*:*"
      ],
      "kev": true,                        // CISA KEV 命中
      "epss": 0.97,                       // FIRST EPSS 分值 0–1
      "epss_percentile": 0.999,
      "summary": "…"                      // 可选，极短描述（不落 UI）
    }
  ]
}
```

**格式要点**：

- **粗粒度 CPE**：只到**厂商 + 产品**（`a:apache:log4j`），**不做版本区间匹配** ——
  版本区间匹配需要完整 CPE 字典（数百 MB），且易错。本工具做的是**暴露面启发式**
  （原则 3 / §9），**产品级匹配**已足够给出「这台机器跑的东西有已知 CVE」的信号。
  ⚠ 因此输出**必须**写「**匹配到**，非**验证过**」（见 §5）。
- **`kev` / `epss` 缺失** → 视为「无该信号」，排序时置后，**不是**「分值 0」的强断言；
  与「查了、KEV 为 false」在内部结构上**可区分**（照 v2.1 §2.3「无数据 ≠ 无漏洞」）。
- **不允许**任何非数据键（无 `"scripts"` / `"rule"` / 可执行片段）—— 原则 2 的硬边界。
- 解析器遇到**未知键** → 忽略（向前兼容）；遇到**未知 `schema`** → warning + 按 v1 尽力解析。

```

scanner/exposure.py         # 零 PyQt / 零第三方 / 零网络
  - banner → 粗粒度 CPE → 候选 CVE（产品级匹配，§4）
  - 排序：KEV 命中优先 → 组内 EPSS 降序
  - 输出结构含「数据新鲜度 + 匹配置信说明」，供 CLI/GUI 呈现
  - 文案硬约束：绝无「已验证/可利用」，只用「匹配到 / 暴露面提示」（§5）
```

## 7. 待决 / 留给 2.3 编码前确认的点

1. **内置种子要不要放**：`resource_dir()` 里是放**空文档**（纯靠用户下载），
   还是放一个**极小的常见 CVE 集**（如 Log4Shell / 永恒之蓝等十来个）？
   —— 建议**放极小集**（让「刚装完、没下载快照」也有基本价值），
   代价是打包 +1 个小文件 + CI 资源断言。**这要在编码前拍板。**
2. **`summary` 字段要不要**：若不落 UI，可省（省体积）；若要给 GUI tooltip，则要。
   —— 建议**保留但可选**，解析器容忍缺失。
3. **`tools/build_cve_snapshot.py` 是否做**：若没有真实的「自己聚合」需求，
   可以**先不做**（只承诺路径 A），避免写一个无人用的脚本。
4. **快照的托管位置**：路径 A 的「社区发布单文件」具体挂哪（本仓库 release /
   独立数据仓库 / 文档里的第三方地址）—— **需要在 2.3 开工前定**，否则用户无处下载。
