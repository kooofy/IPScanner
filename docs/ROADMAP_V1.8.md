1. **一个 minor 只承载 4 项** —— 让「v1.8 交付了什么」能被一句话说清。

## 1. v1.8 四项

### 1.1 定位查询：「这台设备插在哪」（MAC/IP → 交换机端口 + 历史）

| 项 | 值 |
|---|---|
| 优先级 | **P0**（v1.8 主题项） |
| 工时 | **3–5 天** |
| 依赖 | 无（数据已存在） |
| 原编号 | 建议书 v1.8 #1 |

**为什么是它**：把产品从「扫描器」变成「台账」的**最便宜**一步，也是局域网里被问得
最多的问题。同类里 Netdisco 靠这个功能立身。

**现状（已实测，2026-10-10 复核后修正）**：`switch_mapper.py` 已经逐台走 `dot1dTpFdbTable`
（L126），并把 `bridge_port → if_index → port_name` 解析出来了（L212–L220）；
`SwitchInfo.sys_name` + `PortMapping.port_name` **就是**「(交换机, 端口)」二元组 ——
**采集端不用改**。

⚠ **但「缺的不是采集，是索引与查询」这句话只对了一半**：**端口映射从未被持久化**。
实测：`map_switch_ports` 只被 `topology_discovery.py:1119` 与 `ui_threads.py:283`
（`SwitchMapThread`）**按需调用**，结果留在内存里用完即弃；`history_store.py` 的快照库里
只有 `snapshots` 与 `devices` 两张表，**没有任何端口 / 交换机相关表或列**。

→ 所以「上次在 X 口、本次在 Y 口」**目前无从谈起**：没有历史端口数据可比。
**必须先补一层持久化**，本项工时因此比原估略高。

**做法**：
- **新增 `port_map` 表**（随快照写入）：`(snapshot_id, switch_ip, switch_name, mac,
  port_name, port_confidence)`，加 `mac COLLATE NOCASE` 索引与 `snapshot_id` 索引
  （沿用 `devices` 表已有的索引模式）；
- 每次扫描保存快照时，把各交换机的 `SwitchInfo.mappings` 一并落库；
- **`locate(mac | ip | hostname)` 纯查询**：取该 MAC 最近一次出现的快照 → 当前
  `(switch_name, port_name)`；再回溯上一次**端口不同**的快照 → 得出「上次在 X 口」；
- UI：一个搜索框（输入 MAC / IP / 主机名 → 当前端口 + 最近变化）；
- CLI：`ipscanner locate --mac <mac>` 输出 JSON。

⚠ **端口名要带可信度标注**：`switch_mapper.py:214` 在 `if_index` 解析不出来时会回退成
`f"Port {bridge_port}"` —— 那**不是真实端口名**，只是桥接端口号。落库时必须区分
「真端口名」与「仅端口号」，展示时后者要标注不确定，不能当成端口名糊弄过去
（延续本项目的「诚实降级」原则）。

**验收（可写成测试）**：
- 给定 3 台交换机 + 1 个终端 MAC，`locate(mac)` 返回 `(switch_name, port_name)`；
- 同一 MAC 在两次快照间换了端口时，返回「上次在 X 口，本次在 Y 口」；
- 交换机不支持 BRIDGE-MIB（数据不全）时**明确标注「位置未知」**，不猜；
- 端口名只有桥接端口号（无真实 ifName）时，结果里带 `index_only` 标注。

**落地记录（2026-10-10，已完成）**：

- `history_store.py` 新增 `switch_map` / `port_map` 两张表（`snapshot_id` 外键 +
  `ON DELETE CASCADE`，`prune()` 自动清子表）与 `snapshot_id` / `mac COLLATE NOCASE`
  索引；新增 `save_port_map()`（对同一快照**幂等**：先清后写，否则重读一次转发表会让
  端口记录翻倍、假报「换过端口」）与 `locate_device()` 纯查询。
- `switch_mapper.py`：`PortMapping` 新增 `port_is_real`（`ifName` 解析不出来时的
  `"Port 5"` **不是端口名**）；新增 `switch_info_to_dict()` 作为到存储层的桥 ——
  只报告「是否真实端口名」这个**事实**，规范值编码留给存储层，避免领域层反向依赖。
- `topology_discovery.py` 新增 `collect_switch_port_maps()`：复用拓扑发现已有的候选筛选
  （`_select_candidates`）与 SNMP 探测（`_probe_snmp`），只读转发表、不建图。
- **采集入口做成扫描选项**（GUI「读取交换机转发表」/ CLI `--switch-map`），**默认关**：
  每台交换机 5 次 SNMP walk，且会产生额外 SNMP 流量，不能默认跑；采集在**扫描线程内**
  完成（主线程做会把界面冻住），拿到 `snapshot_id` 后再落库。
- 展示层：`scanner/constants.py` 新增 `_LOCATE_REASON_TEXT` / `_LOCATE_REASON_HINT`
  （规范值 → 标签 + 「下一步怎么办」），已登记进 `_label_tables()`；CLI `locate`
  子命令（JSON 保持语言无关，未定位到退出码 **4**）；GUI `ui_dialogs/locate.py`
  （「分析 → 设备定位...」，`Ctrl+L`）。

**验收对照**（`tests/test_locate.py` 32 项 + `tests/test_locate_dialog.py` 14 项 +
`tests/test_cli.py` 8 项）：四条验收标准逐条钉住，另加四种 `reason` 的区分、
`prune` 级联、幂等重写、按 IP / 主机名定位、MAC 大小写、整条链路
「采集 → 落库 → 定位」的端到端用例。

**一处与原计划的偏差**：原计划写的是「每次扫描保存快照时一并落库」，但保存快照的那一刻
`SwitchInfo` 并不存在 —— 转发表要额外发 SNMP 才能拿到。改成**显式开关**后，
「没数据」这件事反而有了明确出口：定位查询会如实报「从未采集过交换机转发表」并告诉
用户怎么开。

### 1.2 被动 / 持续发现模式（扫描器 → 台账的那一步）

| 项 | 值 |
|---|---|
| 优先级 | **P0** |
| 工时 | **5–7 天** |
| 依赖 | 复用 `scanner/dns.py`（已有手写 mDNS） |
| 原编号 | 建议书 v1.8 #2 |

**为什么是它**：这是建议书 §2A 的核心判断 —— 从「我跑一次扫描」到「我有一份会自己更新的台账」。

**现状（已实测）**：
- **mDNS 已是手写实现**：`scanner/dns.py::mdns_discover()`（绑 5353、查
  `_services._dns-sd._udp.local`、解析 PTR）—— **不需要 `zeroconf`**；
- ARP 读取已有：`scanner/ping.py::get_mac_for_ip()`（`arp -a <ip>` 子进程）——
  被动发现要的是**整表 dump**，是它的自然扩展；
- `scheduler.py` 只生成 schtasks / cron 命令（外部调度），**不是常驻循环** ——
  所以需要一个**进程内**轮询。

**做法（刻意收窄范围）**：
- **只做三件**：① 周期性 dump 本机 ARP 表（不发包）；② 周期性复用 `mdns_discover()`
  收组播；③ 把结果并入「当前台账」并触发变更检测；
- **不做**：Windows 服务 / 常驻守护（与建议书 §9「不做常驻监控服务」一致）；
  NDP（属 v1.9 的 IPv6 项）；SSDP 列为可选；
- 运行形态：GUI 打开时进程内定时器 + `ipscanner watch --once` 供 `scheduler` 定时调用。
- ⚠ **修正建议书**：原文写「`zeroconf` mDNS/DNS-SD 常驻」—— 本项目**不用第三方 mDNS**
  （手写实现已在），照原文做会**破坏零依赖身份**。用 `scanner/dns.py` 即可。

**验收（可写成测试）**：
- `watch --once` 能把 ARP 表里的设备并入台账，新增设备在**一个轮询周期内**出现；
- 一条测试断言**被动路径不调用任何主动探测函数**（不发包 → 不惊动 IDS）：
  mock 掉 scanner 的探测入口，断言未被调用；
- 无权限 / 表为空时优雅降级**并记日志**（不静默）。

**落地记录（2026-10-10，已完成）**：

- `scanner/passive.py`（新）：`dump_arp_table()` 读本机 ARP **整表**
  （Windows `arp -a`；Linux 先读 `/proc/net/arp`、失败退 `arp -an`；macOS `arp -an`），
  三种格式各有一个独立解析函数便于喂样本单测；`passive_discover()` 把 ARP 结果与
  mDNS 结果合并成 `{ip: ScanResult}`（复用扫描引擎的 `_merge_mdns`，连
  `mdns_updated` 重渲染契约一起继承）；`PassiveWatcher` 维护跨轮**内存台账**
  并只报「新出现」。
- **「被动」是硬约束，不是形容词**：`mdns_discover()` 原本会主动发 10 个组播查询，
  与本节验收条件「不发包」直接冲突 —— 因此给它加了 `listen_only=True`
  （绑 5353 + 加入组播组，**一个包都不发**），默认走只听；要更全的发现能力才用
  `--mdns-active` 显式开主动查询。
- **只报「出现」，不报「消失」**：ARP 条目会过期，设备从表里消失**不等于**它下线了，
  报「消失」是假阳性。宁可不说，也不给用户一份会自己造谣的台账。
- **不写快照**（本节新增的关键取舍）：快照有 20 条硬上限（`history_store.prune`），
  每周期写一条会在十分钟内把真实扫描历史全冲掉、`diff` 与定位查询随之失效。
  所以被动结果只进内存台账；要落库必须显式 `--save-snapshot`，且
  `--interval` 与 `--save-snapshot` **互斥**（持续轮询 + 落库必然冲掉历史，直接拒绝）。
- 运行形态：CLI `ipscanner watch`（默认单次轮询，`--once` 可显式写出；`--interval`
  进入持续轮询，`--count` 限次；`--fail-on-change` 有新设备时退出码 **2**，
  与 `diff` 同一语义）；GUI 在「设置」菜单加**「持续发现」**开关（默认关，
  与「读取交换机转发表」并列），勾上后由 `QTimer` 每 30 秒起一个
  `PassiveWatchThread` —— **必须在后台线程**，mDNS 只听要占住 5353 听满超时时间，
  放主线程就是界面卡住。
- 基线：`history_store.latest_device_ips()` 取最近一次快照的 IP 集合，
  使「新出现」= 「上次扫描之后新冒出来的设备」；没有快照时基线为空，
  第一次轮询会把整张 ARP 表报成新设备 —— 这是**如实**的（库里确实没有它们的记录）。

**验收对照**（`tests/test_passive.py` 25 项 + `tests/test_cli.py::WatchCommandTest`
11 项）：三条验收标准逐条钉住，其中「不发包」用**假 socket 断言 `sendto` 从未被调用**，
并**反向验证**主动模式下确实会发包（否则那条断言是空的）；另有三种 ARP 表格式、
平台分支（显式 patch `_IS_WINDOWS`，否则 Unix 路径只在 CI 上才被测到）、
表为空时留 warning、mDNS 出错不丢 ARP 结果、只报新出现不报消失、幂等轮询等用例。

**测试暴露出的两个真问题（已修）**：① `/proc/net/arp` 是**按空白切列**读的，
列错位时会把垃圾行当设备 —— 加了统一的 MAC 形状校验；② mDNS 抛异常时会把
**已经读到的 ARP 结果**一起丢掉，改为记 warning 后保留 ARP 结果
（扫描引擎对 mDNS 阶段也是这个处理）。

**一处与原计划的偏差**：原计划写「周期性复用 `mdns_discover()` 收组播」，
但该函数**会发包**，与同一节的验收条件自相矛盾。按「不发包」这条更硬的标准
（也是本节存在的理由：不惊动 IDS）加了只听模式，并把主动查询降级为可选开关。

### 1.3 历史查询后台化（分页 + LIMIT + 过滤下推）

| 项 | 值 |
|---|---|
| 优先级 | **P1**（真实缺陷 + 规模化前置） |
| 工时 | **1–2 天** |
| 依赖 | 复用 `ui_threads.py`（已有 6 个 `QThread` 类） |
| 原编号 | 建议书 v1.8 #5（原文列为「配套小改动」） |

**为什么是它**：这是**已实测的真 bug**，不是「优化」。

**现状（已实测）**：`ui_dialogs/history.py::_run_query()`（L260）**同步跑在 GUI 线程**，
调用 `history_store.query_history()`（L285）—— 后者**没有 LIMIT**、全量取回、
Python 聚合（4 万行 605 ms；`/16` × 20 快照量级会到秒级）。
`ui_threads.py` 已有 6 个 `QThread` 类，但 **`ui_dialogs/` 里一个都没用** ——
用户在大库上点「查询」会**冻结界面**。

**做法**：
- 两个历史对话框的查询搬进 `QThread`（照 `ui_threads.py` 既有模式），加进度与取消；
- `query_history` 加 `limit` / `offset`，把 `device_class` / 网段过滤**下推到 SQL**；
- **不动**资产表（那是 v2，见 §3）。

**验收（可写成测试）**：
- `/16` × 20 快照量级下，查询期间**主线程事件循环可响应**（QTest 断言，而非「看着不卡」）；
- 查询带 `LIMIT`，翻页结果一致；
- 取消能真正中断查询。

**落地记录（2026-10-10，已完成）**：
- `ui_threads.py` 新增 `HistoryQueryThread` / `SnapshotCompareThread`；
  `HistoryQueryDialog` 的查询与导出、`HistoryCompareDialog` 的读快照都搬进后台线程，
  并带「停止」与取消。
- `query_history(..., limit=None, offset=0, cancel_event=None)`：分页 + 真取消
  （`QueryCancelled`）。
- 分页展示（每页 500 行 + 「加载更多」）；**导出始终是完整结果**，不受分页影响。
- 对比对话框改为 `list_snapshots()` 填下拉框 + 按需读那两份快照
  （旧实现在 `__init__` 里 `load_all()`，把全部快照的设备明细都读进来）。

**实测（本机，20 份快照 × 4000 台 = 8 万行）**：

| 查询 | 耗时 |
|---|---|
| 全量（无过滤） | **1363 ms** |
| 带网段过滤（`10.3.0.0/16`） | **228 ms** |
| 带 IP 子串过滤 | 181 ms |

- 聚合循环改用**整数下标**取 `sqlite3.Row`（原按列名取），全量查询 2562 ms → 1363 ms。
- **网段 / IP 子串过滤下推到 SQL**：结果与 Python 侧完全等价（有对拍测试），
  行数在聚合前就被砍掉 —— 这是收益最大的一处。
- ⚠ **`device_class` 刻意不下推**：它比较的是聚合后的「最新已知类型」，按行过滤会把
  `first_seen` 从「首次出现」改成「首次是打印机」。原计划的「类型过滤下推」**不做**，
  理由写进了 `history_store.query_history` 的注释与
  `tests/test_history_query.py::QueryHistoryPushdownTest.test_device_class_is_not_pushed_down`。
- ⚠ **`limit` 不降低查询耗时**：截取发生在过滤与排序之后（否则翻页会看到随机子集），
  所以 LIMIT 买到的是「表格填充量」与「翻页正确性」，不是「查得更快」。
  真正的大库提速要靠**聚合本身下沉到 SQL**，属 v2 资产表那一档的改造。

### 1.4 发布与可见性包（零 / 低成本高杠杆）

| 项 | 值 |
|---|---|
| 优先级 | **P1**（其中签名有长审批周期，**必须最早启动**） |
| 工时 | **2–3 天**（+ 等待审批） |
| 依赖 | 无 |
| 原编号 | 建议书 v1.8 #13 + #14（本重排合并为一个交付单元） |

**为什么是它**：这些是**采纳摩擦**，不是功能。README 决定「要不要装」，
签名决定「装了会不会被拦」。

**做法（4 件小事，同一主题）**：
1. **README 首屏三句话 + 对比表** —— 「一条命令扫完一个网段」/「不限设备·不限站点·
   无需账号·无需上云」/「Windows 免安装包 + CLI + JSON」；再加
   「IPScanner vs Advanced IP Scanner vs SoftPerfect vs TNI」对照表。**零代码**。
2. **申请 SignPath Foundation 签名**（开源免费）—— **审批要时间，先提交**。理由：
   新版 SmartScreen 信誉按「同一签名身份持续发布」累积，越早开始越值钱；
   **不要买 EV**（2024 起不免 SmartScreen）。
3. **release 工作流** —— `v*` tag → 构建 → 生成 `SHA256SUMS` → 上传 Release
   （现在发版是手工的）。
4. **`CHANGELOG.md`**（Keep a Changelog 格式）—— 多机并行开发下，
   版本历史现在只散在 commit 里。

**验收**：

> **耦合提示（#11）**：建议书自己指出「纯 MAC 身份在随机化 MAC 的设备上会每次都当成
> 新设备」。而 **1.2 被动发现会放大变更告警量** —— 若 1.2 上线后变更假阳性明显上升，
> **应把 #11 提前到 v1.8 或紧随其后**，否则「台账」的可信度会被噪声吃掉。

> **#11 落地记录（2026-10-11）**：耦合提示成立 —— 1.2 上线后「按 MAC 认设备」的
> 假阳性确实会被放大，所以 #11 紧随其后做掉，没有拖到 v1.9。
>
> - **判据**：MAC 首字节的 **LAA 位**（本地管理地址）= 随机 MAC 的硬信号。
>   它是**必要不充分**条件（少数虚拟网卡也用 LAA），所以不单凭它下结论 ——
>   还要**指纹一致**才判定「同一台」。
> - **指纹只认身份锚点**（主机名 / 厂商 / 型号 / 序列号）。**明确不用**设备类别 /
>   操作系统 / 服务：它们是**上下文**，在整网里被大量设备共享，会把同型号的两台并成
>   一台。「错认」比「漏认」严重得多 —— 漏认只是多报一次新设备（诚实），错认是让
>   台账凭空少一台、把 A 的历史挂到 B 上。
>   另注：快照表 `devices` 只存 hostname/vendor/device_class/os_guess/open_ports，
>   **没有服务字段** —— 原提示里的「服务组合」在快照对比这条路径上本来就取不到。
> - **产出**：新增变更类型 `mac_randomized`（提示级），取代
>   「新增设备 + 设备消失（+ 同 IP 时的「设备被替换」）」三连假阳性；
>   `PassiveWatcher` 的「新出现」也加了一道指纹关。
> - **诚实降级**：指纹对不上就如实报新增/消失，不猜；同一 IP 换成另一个随机 MAC
>   但没取到可核对的指纹时，不再断言「设备被替换」，降级为提示并写明
>   「未判定是否同一台」。
> - 实现见 `device_fingerprint.py`；测试见 `tests/test_device_fingerprint.py`（35 项）。

> **#4 落地记录（2026-10-11）**：本项的**前置**（1.2 持续状态）与 **#11 变更可信**
> 都已在 v1.8 内交付 —— 于是这一层现在做，而不是拖到 v1.9。理由：被动发现把
> 「变更事件源」从「我跑一次扫描」变成了「它一直在看」，事件量随之上来；
> 变更判定变可信（#11）解决的是**假阳性**，本项解决的是**真阳性里的噪声**
> （计划内维护、已知检修、同一件事反复报）—— 两者是同一枚硬币的两面，
> 缺任何一面，台账的可信度都会被吃掉。
>
> - **产出**：新增 `alert_policy.py`（纯标准库、零 Qt）—— 三类规则编译成可判定的
>   规则集，`evaluate()` 把变更分成「该发」与「被抑制」；配置并入 `notify.json`
>   （`maintenance_windows` / `mutes` / `dedup`），不引入第二个配置文件。
> - **维护窗口**：星期 + 时段，可再叠加网段 / 设备 / 变更类型。支持**跨午夜**
>   （`23:00`–`02:00`，`days` 指**起始日**，与人的直觉一致）与 `工作日` / `周末` 简写。
> - **静音**：MAC / IP / 网段 + 可选类型 + 可选到期时间（只写日期按**当天结束**算）。
>   没写任何身份维度也没写类型的静音会静音一切 —— 视为漏配字段，**忽略并记 warning**。
> - **去重**：`(设备, 变更类型)` 冷却窗口内只发一次。**状态必须落盘**
>   （数据目录 `alert_dedup.json`）—— 定时扫描由系统调度器以**独立进程**拉起
>   （`schtasks` / `cron`），进程内状态活不过一次运行，只存内存等于没有去重。
> - **抑制 ≠ 隐藏（本项最关键的取舍）**：被抑制的变更**照常计入退出码与审计日志**，
>   只是不发通知。「静音」是给人耳的，「退出码」是给机器的 —— CI 需要真实信号，
>   不该被静音吃掉。因此 `--fail-on-change` 的语义**完全不受**策略影响。
> - **发送成功才记账**：`evaluate()` 只**读**去重状态，调用方在渠道发送成功之后才
>   `record()`。全部渠道失败时不记账，下一轮会重试 —— 否则一次网络抖动会让这条
>   变更永远沉默（去重把它当成「已经报过了」）。这是去重最容易写错的地方。
> - **不静默**：部分抑制时，告警正文附一行「另有 N 条被抑制」；全部抑制时一条都不发，
>   但本地日志写明条数与原因（维护窗口 / 静音 / 去重各几条）。
> - **失败安全（fail-open）**：配置写错一律**不抑制**（宁可多报，不可漏报）；
>   单条规则解析失败只记 warning 并跳过，不影响其余规则。`start == end` 视为空窗口。
> - 新增 `--no-policy`：忽略全部策略、所有变更都发送（排障用，与 `--no-notify` 对称）。
> - 实现见 `alert_policy.py`；测试见 `tests/test_alert_policy.py`（72 项）+
>   `tests/test_cli.py::NotifyPolicyTest`（12 项，含「发送失败不记账」这条回归守卫）。
>   另用 `.git/_smoke_alert_policy.py` 起**真实本地 HTTP 服务**当 webhook，
>   跑通 `notify.json → build_notifiers → post_json → _notify_changes` 整条链路。

> **#3 落地记录（2026-10-11，第一刀：TLS 到期）**：本项含四类信号，一次性做完是
> 一两周的量，且中途无法验收。于是按**能否独立验收**切成四刀，先做最干净的一刀 ——
> **TLS 证书到期**（半天量级）。切它的理由：
>
> 1. **不新增任何探测**。证书来自扫描**本来就要做**的那次 HTTPS 握手，只是顺手
>    把 DER 也读出来。多发包为零 → 「零利用」这条红线天然成立。
> 2. **顺带修掉一个真实老 bug**。`scanner/http.py` 的 HTTPS banner 一直在
>    `verify_mode = CERT_NONE` 下读 `cert["subject"]` 取 CN —— 而该模式下
>    `getpeercert()` 返回的是**空 dict**（不是 None、也不报错），所以那十行
>    **从未执行过**，banner 恒为 `"…: unknown service"`。实测 `api.github.com`
>    的真实 CN 是 `*.github.com`。这个 bug 是白捡的。
> 3. **半天能做完且能验收**。做完立刻在风险列看到新理由，且不影响其余三刀。
>
> - **零依赖约束下的唯一路径**：`cryptography` 未安装（项目身份是零第三方依赖，
>   不为这一项破例）；`SSLContext.set_verify(CERT_NONE, cb)` 这个老办法在
>   Python 3.13 已被移除（实测 `AttributeError`）。于是只剩
>   `getpeercert(binary_form=True)` 拿 DER 自己走查 —— 新增 `scanner/x509.py`，
>   手写**最小** DER 走查，按 RFC 5280 §4.1 顺序定位字段，只取九项，
>   **不验签、不验链、不做信任判断**。
> - **UTCTime 的两位年按 RFC 5280 §4.1.2.5.1 判**（50–99 → 19xx，00–49 → 20xx），
>   **不是** `strptime("%y")` 的 POSIX 规则（69–99 → 19xx）。两者在 **50–68**
>   这段不一样，用 `%y` 会把 2068 读成 1968 —— 有专门的边界用例钉住。
> - **自签名只值 5 分（本刀最关键的标定）**。局域网设备管理面几乎人手一张自签
>   证书，给高分会让整列风险分塌成一个数。真正的信号是「功能上已经坏了」
>   （过期，40 分）与「有已知攻击」（MD5/SHA-1 25 分、密钥过短 20 分）。
> - **落库用竖表 `security_findings`，不给 `devices` 加列**。`CREATE TABLE
>   IF NOT EXISTS` 对已有库直接生效，而加列必须写 `ALTER TABLE` 迁移，每加一个
>   信号就得再来一次；后面三刀的信号（SMB 方言与签名、LLMNR/NBNS 响应器、
>   弱协议聚合）都是异质枚举/布尔，竖表天然容纳，**schema 不用再动**。
>   与 `switch_map` / `port_map` 同一惯例：允许某次快照一行都没有，带外键 +
>   CASCADE，`prune()` 自动清。
> - **事实走既有的快照路径**（`save_snapshot` / `get_snapshot`），不是另开一个
>   `save_security_findings()` —— 后者迟早会有人忘记调，而「命令行存的快照没有
>   安全事实」这种不一致在界面上看不出来。
> - **存事实，不存结论**。表里是 `(kind, value)` 规范代码（`tls_not_after` 等），
>   没有"已过期 / 自签名"这种判定；阈值只活在 `risk_rules` 一处，日后调整可以
>   从事实重新推导。
> - **验证方式**：手写走查与 Python 自带解析器在**三台真实主机**（
>   `api.github.com` 1010 字节 EC、`www.baidu.com` 2543 字节 RSA）+ 一份本地
>   openssl 现生成的自签名证书上逐字段一致；fuzz 用「证书形状」生成器
>   （实测非空率 **65.1%**，而纯随机字节是 **0%** —— 形状不对就立刻返回）+ 真实
>   证书变异（28.4%），三种 × 8000 条，零未捕获异常。
> - 实现见 `scanner/x509.py` + `scanner/http.py::read_https` +
>   `risk_rules.tls_reasons()`；测试见 `tests/test_x509.py`（46 项，含**本地回环
>   TLS 服务端**，不出网）、`tests/test_risk_rules.py::TlsReasonTest`（18 项）、
>   `tests/test_history_store.py` 两个新类、`tests/test_ui_logic.py` /
>   `tests/test_cli.py` / `tests/test_engine_scan_pipeline.py` 各一组接线用例。
>   另用 `.git/_probe_tls_tests.py` 做**反向验证**：给 11 处关键逻辑逐个注入
>   缺陷，确认对应测试真的会红。
> - **剩余三刀仍未动工**：SMB 方言 / 签名（只发 NEGOTIATE，**绝不**尝试认证）、
>   LLMNR / NBNS 响应器（只查询或只听，**绝不**投毒）、弱协议聚合。三者的
>   `security_findings` 落库位置已就位，不需要再改 schema。

> **#3 落地记录（2026-10-11，第二刀：LLMNR / NBNS 响应器）**：第一刀（TLS）的
> 红利在第二刀上立刻兑现 —— **schema 一行没改**，竖表 `security_findings` 直接
> 容纳了新信号；事实照旧走既有快照路径，GUI 与 CLI 两个落库入口自动带上。
>
> - **这一刀与第一刀有一个本质差别：它会往网络里发包**。TLS 证书来自扫描本来
>   就要做的那次握手（多发包为零），而 LLMNR/NBNS 探测必须主动发一个查询。
>   于是它由**显式开关**控制、**默认关**（GUI 勾选框「探测名字响应器」/ CLI
>   `--name-responder`）—— 与「读取交换机转发表」「持续发现」并列成一组
>   "会碰网络的采集行为"。默认关这条有专门测试钉住（`test_defaults_to_off`）。
> - **红线**：只做两件事 —— 构造一个查询、解析收到的应答。不注册名字、不应答
>   别人的查询、不伪造 MAC/IP、**绝不向网络投毒**。发出去的只是一个标准 DNS
>   格式的查询包，与一台普通 Windows 机器在 DNS 解析失败时自动发出的东西
>   **完全一样**，不含任何攻击性载荷。这条写在模块 docstring 第一段。
> - **零利用版本的做法**：编一个**不可能存在**的名字（随机后缀）查一次，看谁给
>   **肯定应答**。干净网络里没有任何主机会应答 —— 名字根本不归它所有。一台主机
>   若对一个刚编出来的名字给出肯定应答，说明它**在应答它不拥有的名字**：要么是
>   安全工具 / 蜜罐，要么就是欺骗响应器（Responder 那条攻击链的起点）。
> - **三条防误报的判定**（每条都对应一类真实误报）：
>   1. **只认肯定应答**。NBNS 的 RCODE=3「名字不存在」是 WINS 服务器与代理对
>      **每个**不存在名字的正常反应 —— 算成发现等于把每个网段里的 WINS 服务器
>      都报成欺骗响应器。只记 debug。
>   2. **应答里必须真的含我们编的那个名字**。网络里随时有**别人**的
>      LLMNR/NBNS 流量在飘，只看"收到一个肯定应答"会把它们全算进来。
>   3. **随机后缀**。固定名字迟早会有人真的注册它，那时探测就变成永久误报。
> - **两个协议各一个查询构造**：LLMNR（UDP/5355，组播 `224.0.0.252`）的 **RD 位
>   必须为 0**（RFC 4795 §2.1，与普通 DNS 查询的 `0x0100` 不同，最容易抄错）、
>   QTYPE 用 ANY(255)；NBNS（UDP/137，广播 `255.255.255.255`）用 QTYPE=**0x20**
>   （NB，"这个名字的地址是多少"），**刻意不同于** `netbios.py` 已有的 NBSTAT
>   `0x21`（"你注册了哪些名字"）。探测名两个协议共用，故总长 ≤15 字符
>   （NetBIOS 名上限，第 16 字节是类型后缀）—— 超了会被 `_nbt_name16()` 悄悄
>   截断、名字对不上、探测从此静默失效，所以有专门的定长用例。
> - **绑临时源端口而不是 5355/137**：那两个端口本机常被系统解析器占着，而两个
>   协议按规范都是**单播回查询源端口**，临时端口一样收得到。
> - **风险评分只给一个理由代码、不分协议，30 分**（`risk_rules.responder_reasons()`）。
>   同一台主机对两个协议都给肯定应答是**同一个发现**，拆两条会让风险栏出现两条
>   近义理由、分数还翻倍；协议明细留在事实层（`security_findings` 的
>   `llmnr_responder` / `nbns_responder` 两行）—— 这正是"事实与结论分开"的用法。
>   30 分（与 Telnet 明文同级）而不是更高：这个发现本身是**歧义的**，应答不存在
>   名字的既可能是攻击也可能是防护，分数只表示"值得看一眼"，不替用户断定恶意。
> - **范围外的响应器不伪造成设备行**。`apply_responders()` 把结果挂到本次扫到的
>   设备上，返回不在结果里的 IP 列表；调用方（GUI / CLI）只把它们写进日志 ——
>   快照记的是台账，往台账里塞一台没扫到的设备会让设备数失真。
> - **验证方式**：`.git/_llmnr_smoke.py` 在真机上确认本机可发可收组播
>   `224.0.0.252:5355` 与广播 `255.255.255.255:137`，并跑通三种假响应器情形
>   （**不进 CI**：组播/广播在 CI 容器里不一定可用）。进 CI 的测试全部走
>   `targets` 注入指向**回环**假响应器，**绝不往真实组播、广播地址发包** ——
>   真发包的测试会时绿时红，那比没有测试更糟。
> - 实现见 `scanner/llmnr_nbns.py`；测试见 `tests/test_llmnr_nbns.py`（39 项）、
>   `tests/test_scan_options.py`（15 项，含"关着时一个包都不发"）、
>   `tests/test_risk_rules.py::ResponderReasonTest`、
>   `tests/test_history_store.py::ResponderFactsTest`，以及
>   `tests/test_ui_logic.py` / `tests/test_cli.py` 的接线用例。另用
>   `.git/_probe_responder_tests.py` 做**反向验证**：给 22 处关键逻辑逐个注入
>   缺陷（含"抄错 RD 位""把否定应答当发现""不核对名字""两个协议各算一次分"
>   "关着也发包"），确认对应测试真的会红。
> - **剩余两刀仍未动工**：弱协议聚合、SMB 方言 / 签名（只发 NEGOTIATE，
>   **绝不**尝试认证）。
