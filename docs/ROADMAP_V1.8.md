## 0. 重排原则

1. **一个 minor 只承载 4 项** —— 让「v1.8 交付了什么」能被一句话说清。
2. **四项各占一个不可替代的角色**：
   - ① 定义产品身份（「台账」）—— **定位查询**；
   - ② 完成形态转变（事件驱动 → 状态驱动）—— **被动发现**；
   - ③ 修一个**真实缺陷**（GUI 冻结）—— **历史查询后台化**；
   - ④ 降低**采纳摩擦**（零/低成本、高杠杆）—— **发布与可见性包**。
3. **优先级不由「重要」决定，由「是否阻塞其它项」决定** —— 历史查询后台化虽然
   「只是个修复」，但它是规模化的前置，因此进 v1.8。
4. **保持项目身份** —— 不引入任何第三方依赖（§1.2 对原文「zeroconf」的修正即因此）。

## 1. v1.8 四项

### 1.1 定位查询：「这台设备插在哪」（MAC/IP → 交换机端口 + 历史）

| 项 | 值 |
|---|---|
| 优先级 | **P0**（v1.8 主题项） |
| 工时 | **3–5 天** |
| 依赖 | 无（数据已存在） |
| 原编号 | 建议书 v1.8 #1 |

**为什么是它**：把产品从「扫描器」变成「台账」的**最便宜**一步，也是局域网里被问得
最多的问题。同类里 Netdisco 靠这个功能立身。

**现状（已实测，2026-10-10 复核后修正）**：`switch_mapper.py` 已经逐台走 `dot1dTpFdbTable`
（L126），并把 `bridge_port → if_index → port_name` 解析出来了（L212–L220）；
`SwitchInfo.sys_name` + `PortMapping.port_name` **就是**「(交换机, 端口)」二元组 ——
**采集端不用改**。

⚠ **但「缺的不是采集，是索引与查询」这句话只对了一半**：**端口映射从未被持久化**。
实测：`map_switch_ports` 只被 `topology_discovery.py:1119` 与 `ui_threads.py:283`
（`SwitchMapThread`）**按需调用**，结果留在内存里用完即弃；`history_store.py` 的快照库里
只有 `snapshots` 与 `devices` 两张表，**没有任何端口 / 交换机相关表或列**。

→ 所以「上次在 X 口、本次在 Y 口」**目前无从谈起**：没有历史端口数据可比。
**必须先补一层持久化**，本项工时因此比原估略高。

**做法**：
- **新增 `port_map` 表**（随快照写入）：`(snapshot_id, switch_ip, switch_name, mac,
  port_name, port_confidence)`，加 `mac COLLATE NOCASE` 索引与 `snapshot_id` 索引
  （沿用 `devices` 表已有的索引模式）；
- 每次扫描保存快照时，把各交换机的 `SwitchInfo.mappings` 一并落库；
- **`locate(mac | ip | hostname)` 纯查询**：取该 MAC 最近一次出现的快照 → 当前
  `(switch_name, port_name)`；再回溯上一次**端口不同**的快照 → 得出「上次在 X 口」；
- UI：一个搜索框（输入 MAC / IP / 主机名 → 当前端口 + 最近变化）；
- CLI：`ipscanner locate --mac <mac>` 输出 JSON。

⚠ **端口名要带可信度标注**：`switch_mapper.py:214` 在 `if_index` 解析不出来时会回退成
`f"Port {bridge_port}"` —— 那**不是真实端口名**，只是桥接端口号。落库时必须区分
「真端口名」与「仅端口号」，展示时后者要标注不确定，不能当成端口名糊弄过去
（延续本项目的「诚实降级」原则）。

**验收（可写成测试）**：
- 给定 3 台交换机 + 1 个终端 MAC，`locate(mac)` 返回 `(switch_name, port_name)`；
- 同一 MAC 在两次快照间换了端口时，返回「上次在 X 口，本次在 Y 口」；
- 交换机不支持 BRIDGE-MIB（数据不全）时**明确标注「位置未知」**，不猜；
- 端口名只有桥接端口号（无真实 ifName）时，结果里带 `index_only` 标注。

### 1.2 被动 / 持续发现模式（扫描器 → 台账的那一步）

| 项 | 值 |
|---|---|
| 优先级 | **P0** |
| 工时 | **5–7 天** |
| 依赖 | 复用 `scanner/dns.py`（已有手写 mDNS） |
| 原编号 | 建议书 v1.8 #2 |

**为什么是它**：这是建议书 §2A 的核心判断 —— 从「我跑一次扫描」到「我有一份会自己更新的台账」。

**现状（已实测）**：
- **mDNS 已是手写实现**：`scanner/dns.py::mdns_discover()`（绑 5353、查
  `_services._dns-sd._udp.local`、解析 PTR）—— **不需要 `zeroconf`**；
- ARP 读取已有：`scanner/ping.py::get_mac_for_ip()`（`arp -a <ip>` 子进程）——
  被动发现要的是**整表 dump**，是它的自然扩展；
- `scheduler.py` 只生成 schtasks / cron 命令（外部调度），**不是常驻循环** ——
  所以需要一个**进程内**轮询。

**做法（刻意收窄范围）**：
- **只做三件**：① 周期性 dump 本机 ARP 表（不发包）；② 周期性复用 `mdns_discover()`
  收组播；③ 把结果并入「当前台账」并触发变更检测；
- **不做**：Windows 服务 / 常驻守护（与建议书 §9「不做常驻监控服务」一致）；
  NDP（属 v1.9 的 IPv6 项）；SSDP 列为可选；
- 运行形态：GUI 打开时进程内定时器 + `ipscanner watch --once` 供 `scheduler` 定时调用。
- ⚠ **修正建议书**：原文写「`zeroconf` mDNS/DNS-SD 常驻」—— 本项目**不用第三方 mDNS**
  （手写实现已在），照原文做会**破坏零依赖身份**。用 `scanner/dns.py` 即可。

**验收（可写成测试）**：
- `watch --once` 能把 ARP 表里的设备并入台账，新增设备在**一个轮询周期内**出现；
- 一条测试断言**被动路径不调用任何主动探测函数**（不发包 → 不惊动 IDS）：
  mock 掉 scanner 的探测入口，断言未被调用；
- 无权限 / 表为空时优雅降级**并记日志**（不静默）。

### 1.3 历史查询后台化（分页 + LIMIT + 过滤下推）

| 项 | 值 |
|---|---|
| 优先级 | **P1**（真实缺陷 + 规模化前置） |
| 工时 | **1–2 天** |
| 依赖 | 复用 `ui_threads.py`（已有 6 个 `QThread` 类） |
| 原编号 | 建议书 v1.8 #5（原文列为「配套小改动」） |

**为什么是它**：这是**已实测的真 bug**，不是「优化」。

**现状（已实测）**：`ui_dialogs/history.py::_run_query()`（L260）**同步跑在 GUI 线程**，
调用 `history_store.query_history()`（L285）—— 后者**没有 LIMIT**、全量取回、
Python 聚合（4 万行 605 ms；`/16` × 20 快照量级会到秒级）。
`ui_threads.py` 已有 6 个 `QThread` 类，但 **`ui_dialogs/` 里一个都没用** ——
用户在大库上点「查询」会**冻结界面**。

**做法**：
- 两个历史对话框的查询搬进 `QThread`（照 `ui_threads.py` 既有模式），加进度与取消；
- `query_history` 加 `limit` / `offset`，把 `device_class` / 网段过滤**下推到 SQL**；
- **不动**资产表（那是 v2，见 §3）。

**验收（可写成测试）**：
- `/16` × 20 快照量级下，查询期间**主线程事件循环可响应**（QTest 断言，而非「看着不卡」）；
- 查询带 `LIMIT`，翻页结果一致；
- 取消能真正中断查询。

**落地记录（2026-10-10，已完成）**：
- `ui_threads.py` 新增 `HistoryQueryThread` / `SnapshotCompareThread`；
  `HistoryQueryDialog` 的查询与导出、`HistoryCompareDialog` 的读快照都搬进后台线程，
  并带「停止」与取消。
- `query_history(..., limit=None, offset=0, cancel_event=None)`：分页 + 真取消
  （`QueryCancelled`）。
- 分页展示（每页 500 行 + 「加载更多」）；**导出始终是完整结果**，不受分页影响。
- 对比对话框改为 `list_snapshots()` 填下拉框 + 按需读那两份快照
  （旧实现在 `__init__` 里 `load_all()`，把全部快照的设备明细都读进来）。

**实测（本机，20 份快照 × 4000 台 = 8 万行）**：

| 查询 | 耗时 |
|---|---|
| 全量（无过滤） | **1363 ms** |
| 带网段过滤（`10.3.0.0/16`） | **228 ms** |
| 带 IP 子串过滤 | 181 ms |

- 聚合循环改用**整数下标**取 `sqlite3.Row`（原按列名取），全量查询 2562 ms → 1363 ms。
- **网段 / IP 子串过滤下推到 SQL**：结果与 Python 侧完全等价（有对拍测试），
  行数在聚合前就被砍掉 —— 这是收益最大的一处。
- ⚠ **`device_class` 刻意不下推**：它比较的是聚合后的「最新已知类型」，按行过滤会把
  `first_seen` 从「首次出现」改成「首次是打印机」。原计划的「类型过滤下推」**不做**，
  理由写进了 `history_store.query_history` 的注释与
  `tests/test_history_query.py::QueryHistoryPushdownTest.test_device_class_is_not_pushed_down`。
- ⚠ **`limit` 不降低查询耗时**：截取发生在过滤与排序之后（否则翻页会看到随机子集），
  所以 LIMIT 买到的是「表格填充量」与「翻页正确性」，不是「查得更快」。
  真正的大库提速要靠**聚合本身下沉到 SQL**，属 v2 资产表那一档的改造。

### 1.4 发布与可见性包（零 / 低成本高杠杆）

| 项 | 值 |
|---|---|
| 优先级 | **P1**（其中签名有长审批周期，**必须最早启动**） |
| 工时 | **2–3 天**（+ 等待审批） |
| 依赖 | 无 |
| 原编号 | 建议书 v1.8 #13 + #14（本重排合并为一个交付单元） |

**为什么是它**：这些是**采纳摩擦**，不是功能。README 决定「要不要装」，
签名决定「装了会不会被拦」。

**做法（4 件小事，同一主题）**：
1. **README 首屏三句话 + 对比表** —— 「一条命令扫完一个网段」/「不限设备·不限站点·
   无需账号·无需上云」/「Windows 免安装包 + CLI + JSON」；再加
   「IPScanner vs Advanced IP Scanner vs SoftPerfect vs TNI」对照表。**零代码**。
2. **申请 SignPath Foundation 签名**（开源免费）—— **审批要时间，先提交**。理由：
   新版 SmartScreen 信誉按「同一签名身份持续发布」累积，越早开始越值钱；
   **不要买 EV**（2024 起不免 SmartScreen）。
3. **release 工作流** —— `v*` tag → 构建 → 生成 `SHA256SUMS` → 上传 Release
   （现在发版是手工的）。
4. **`CHANGELOG.md`**（Keep a Changelog 格式）—— 多机并行开发下，
   版本历史现在只散在 commit 里。

**验收**：
- README 首屏含上述三句与对比表；
- `CHANGELOG.md` 存在且覆盖 1.7.x；
- 推 `v*` tag 能自动产出带 `SHA256SUMS` 的 Release；
- SignPath 申请已提交（拿到证书后补签首个版本）。

**落地记录（2026-10-10）**：
- ✅ README 首屏三句话 + 新增「横向对比」小节（对照 Advanced IP Scanner /
  SoftPerfect / TNI 6，来源 `docs/research/`）。
- ✅ `CHANGELOG.md`（Keep a Changelog 格式，覆盖 1.0 → 1.7.6）。

  `SHA256SUMS.txt` → `gh release create`。用 runner 预装的 `gh`，不引第三方 action。
- ⏸ **SignPath 申请暂缓提交**（2026-10-10 决定，提交动作需要项目所有者操作）：
  材料已备齐，见 [`docs/SIGNPATH_APPLICATION.md`](SIGNPATH_APPLICATION.md) —— 含资格自查、
  **九个**表单字段的可粘贴内容（主页 / 仓库 / 许可 / 下载页 / Tagline / 分类 /
  构建系统 / Reputation / 描述）、**提交前的加分准备清单**（§4）、

## 3. 被移出 v1.8 的 10 项及去向

> **不是丢弃，是排期。** 每项都写明「为什么不在 v1.8」。

| 原编号 | 事项 | 去向 | 理由 |
|---|---|---|---|
| #3 | 零利用安全体检（TLS 到期 / SMB / 弱协议 / LLMNR·NBNS） | **v1.9** | 高价值但非「台账」主题；需先把新字段接进风险评分 |
| #4 | 维护窗口 / 告警抑制 / 通知去重 | **v1.9** | 依赖「持续状态」这一**前置**（即本项 1.2 的产物），v1.8 做不完 |
| #6 | 只读 HTTP API + 结构化 webhook | **v1.9** | 领域层零 Qt、接线即可，但受众是「集成派」，晚一轮 |
| #7 | 互操作导出包（Nmap XML / Zabbix LLD / NetBox CSV / Oxidized） | **v1.9** | 同上；其中 **Nmap XML 产出**可提前到补丁轨道（一天换一生态） |
| #8 | 通知渠道走 Apprise | **v1.9** | **会引入第三方依赖**，需单独论证是否破坏零依赖身份 |
| #9 | 拓扑过宽折行 + 文本版导出 | **v1.9** | 体验项，不与 v1.8 主题冲突 |
| #10 | HTML/PDF 报表模板 + 定时报表 | **v1.9** | 依赖已具备（scheduler + HTML 导出），但非主题 |
| #11 | 随机化 MAC 识别 | **v1.9**（**风险耦合**，见下） | 见「耦合提示」 |
| #12 | `user_version` + 覆盖率 / pyright / `pip-audit` + BER fuzz | **拆分** | BER fuzz、`user_version` 进**补丁轨道**；质量门禁进 v1.9 |
| #15 | 拓扑手工校正（钉住 / 隐藏 / 备注） | **v1.9** | 体验项 |

> **耦合提示（#11）**：建议书自己指出「纯 MAC 身份在随机化 MAC 的设备上会每次都当成
> 新设备」。而 **1.2 被动发现会放大变更告警量** —— 若 1.2 上线后变更假阳性明显上升，
> **应把 #11 提前到 v1.8 或紧随其后**，否则「台账」的可信度会被噪声吃掉。

> **资产表（建议书 §4.3 / §5.1，原文标 P0）**：本重排**明确推到 v2**。
> 理由：1.3 已解决眼下最痛的「GUI 冻结」；资产表是 1–2 周的架构改动，
> 应等 1.1 / 1.2 把「台账」用起来、需求变清楚之后再动，避免为想象中的 `/16 × 20`
> 场景先付重构成本。

## 4. 与建议书的差异（我改了什么）

| # | 建议书原文 | 本重排 | 理由 |
|---|---|---|---|
| 1 | v1.8 = 15 项 / 4–6 周 | v1.8 = **4 项** / 2.5–3.5 周 | 单人产能；列 15 件交 4 件的概率极高 |
